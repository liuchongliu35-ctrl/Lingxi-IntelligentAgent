# Runtime / CLI / API 设计问题回答（2）

本文档用于第二轮确认 Runtime / CLI / API 层的落地细节。请直接在每个“你的回答：”后面填写答案。

第一轮已经确认的大方向：

```text
1. Runtime / CLI / API 统一放在 src/app/ 下。
2. Runtime 是应用编排、依赖装配、会话生命周期和结果归一化层。
3. CLI / API 共享同一套 Runtime，不各自实现 Agent 主流程。
4. 正式 Runtime 模式下使用 manage_memory=False，消息写入由 Runtime / Memory 负责。
5. Runtime 统一接管 ReActExecutor 事件回调。
6. Runtime 同时保留 ExecutionResult 和 OutputFeedback。
7. CLI 使用 Typer。
8. API 使用 FastAPI。
9. API 第一版需要 WebSocket 流式能力。
10. main.py 收敛为薄启动器。
```

本轮只讨论实现前必须钉住的细节，不再重复大方向。

## 1. RuntimeResult 协议

### 问题 1：Runtime 对外返回的 `RuntimeResult` 需要包含哪些固定字段？

通俗解释：
Runtime 会同时服务 CLI 和 API，所以它不能只返回字符串，也不能直接把内部对象原样抛给上层。需要一个稳定的结果对象。

建议：
第一版 `RuntimeResult` 固定包含：

```text
success: bool
status: str
session_id: str
run_id: str
output: str
execution_result: dict | None
output_feedback: dict | None
memory_result: dict | None
timeline: list[dict]
requires_user_input: bool
pending_confirmation: dict | None
request_replan: bool
replan_reason: str | None
error_code: str | None
error_message: str | None
persistence_available: bool
persistence_warning: str | None
metadata: dict
```

其中：
- `output` 是给 CLI 默认打印的最终文本。
- `execution_result` 保留执行器结构化结果。
- `output_feedback` 保留用户可见反馈结构。
- `memory_result` 保留 Memory complete/fail 的结果。
- `timeline` 用于 API/CLI 回放。

为什么要问：
这个对象会成为 CLI/API 的共同依赖，后续不应频繁变动。

你的回答：采取你的建议

---

### 问题 2：Runtime 是否需要单独定义 `RuntimeEvent`，还是直接转发 ReActExecutor 的 `ExecutionEvent`？

通俗解释：
ReActExecutor 已经有 `ExecutionEvent`，但 Runtime 可能需要补充 session_id、run_id、source、sequence 等外层信息。

建议：
定义轻量 `RuntimeEvent` 包装：

```text
event_id
session_id
run_id
event_type
message
visible_to_user
payload
source_event
sequence
created_at
```

但不要改变原始事件含义。RuntimeEvent 只是对外传输格式，不是新的执行事件体系。

为什么要问：
WebSocket / CLI 流式输出最好不要直接依赖执行器内部对象形态。

你的回答：采取你的建议

---

### 问题 3：RuntimeResult 中是否允许包含内部调试信息？

通俗解释：
开发调试时可能想看更多字段，但普通用户和 API 调用方不应该看到内部 prompt、隐藏推理或 raw tool output。

建议：
默认不包含内部调试信息。只在显式 `debug=True` 时返回额外诊断字段，并且仍然必须脱敏。

建议字段：

```text
metadata.debug:
  analyzer_summary
  plan_summary
  event_count
  model_profile
  tool_profile
```

禁止字段：

```text
raw_prompt
full_prompt
hidden_reasoning
raw_tool_result
raw_observation
api_key
token
cookie
password
```

为什么要问：
这会影响 API 安全边界和 CLI `--debug` 行为。

你的回答：采取你的建议

## 2. WebSocket 流式协议

### 问题 4：API WebSocket 第一版采用什么路径？

通俗解释：
WebSocket 需要一个稳定连接地址，前端或调用端才能连接并发送消息。

建议：
第一版使用：

```text
WS /ws/sessions/{session_id}/runs
```

如果没有 session_id，需要先用 `POST /sessions` 创建。这样会话边界更清晰。

可选备用：

```text
WS /ws/runs
```

客户端在首条消息里传 session_id。这个更灵活，但第一版更容易混乱。

我的建议：
优先 `WS /ws/sessions/{session_id}/runs`。

为什么要问：
路径设计会影响 API 资源模型和前端接入方式。

你的回答：采取你的建议，备用的那个就不需要了

---

### 问题 5：WebSocket 客户端发给服务端的消息格式怎么定义？

通俗解释：
WebSocket 不是普通 POST，请求参数要通过 JSON 消息传进去。

建议：
第一版客户端发送：

```json
{
  "type": "run",
  "input": "用户输入",
  "stream": true,
  "debug": false,
  "metadata": {}
}
```

后续确认/恢复可以发送：

```json
{
  "type": "resume",
  "run_id": "...",
  "approved": true,
  "confirmation_id": "...",
  "preview_hash": "..."
}
```

为什么要问：
这决定 WebSocket 是只能发起新任务，还是后续可以承载确认/恢复。

你的回答：采取你的建议

---

### 问题 6：WebSocket 服务端推送给客户端的事件格式怎么定义？

通俗解释：
执行过程中会有多种消息：开始、进度、工具、确认、完成、错误。

建议：
统一推送格式：

```json
{
  "type": "event",
  "session_id": "...",
  "run_id": "...",
  "event_type": "tool_started",
  "message": "正在读取文件",
  "visible_to_user": true,
  "payload": {},
  "sequence": 1
}
```

最终完成推送：

```json
{
  "type": "result",
  "session_id": "...",
  "run_id": "...",
  "result": {...}
}
```

错误推送：

```json
{
  "type": "error",
  "code": "runtime_error",
  "message": "...",
  "session_id": "...",
  "run_id": "..."
}
```

为什么要问：
这决定前端/调用端如何统一消费流式数据。

你的回答：采取你的建议

---

### 问题 7：WebSocket 第一版是否需要支持一个连接内多轮对话？

通俗解释：
一种方式是每次运行建立一次连接，运行结束就关闭；另一种是一个连接持续多轮。

建议：
第一版支持一个连接内多轮对话，但实现上保持简单：

```text
客户端每发送一条 type=run，就启动一轮。
同一个连接内默认串行执行。
上一轮未结束前，不允许同连接再启动新 run。
```

为什么要问：
这会影响并发控制和连接生命周期。

你的回答：采取你的建议，同一个websocket连接在同一时间只能有一个正在运行的对话，不处理新的用户发起的对话，用户发起的新对话可以放到等待队列，等当前正在运行的对话结束后再将队列里面的拿出来跑

## 5. Resume / Cancel / Delete / Export 行为

### 问题 16：`resume` 第一版主要用于确认恢复，还是也要支持断点续跑？

通俗解释：
确认恢复是“用户同意/拒绝某个危险动作后继续”。断点续跑是“进程中断后从中间状态继续执行”，难度大很多。

建议：
第一版只支持确认恢复：

```text
RuntimeResult.status = waiting_user
pending_confirmation 存在
用户确认或拒绝
Runtime.resume(...) 调用 ReActExecutor.resume_after_confirmation(...)
```

不承诺跨进程断点续跑。程序重启后的 running/waiting_user run 由 Memory 标记为 interrupted。

为什么要问：
这关系到第一版范围是否会爆炸。

你的回答：采取你的建议，第一版不做断点续跑，这个涉及的东西太多，第一版只支持确认恢复

---

### 问题 17：`cancel` 第一版应该取消什么？

通俗解释：
取消可以表示取消当前等待确认，也可以表示中断正在执行的任务。

建议：
第一版先支持取消等待确认的 run：

```text
waiting_user -> cancelled
记录用户取消事件
不继续执行 pending action
```

不承诺强制中断正在运行的线程或工具进程。正在执行中的取消留给后续异步任务系统。

为什么要问：
同步 Runtime 下强行取消正在执行的工具很复杂，第一版应避免虚假承诺。

你的回答：采取你的建议

---

通俗解释：


如果你希望可恢复，后续再增加 archive/soft delete。

为什么要问：
这会影响用户数据保留策略。

你的回答：采取你的建议

## 6. Runtime Factory 和依赖生命周期

### 问题 20：Runtime 依赖是进程级单例，还是每次请求重新创建？

通俗解释：
ModelManager、ToolManager、SessionManager 这些对象创建成本和状态不同。

建议：
第一版采用进程级 Runtime 实例：

```text
API 启动时创建一个 Runtime。
CLI 每次启动创建一个 Runtime。
单个 Runtime 内共享 ModelManager / ToolManager / SessionManager。
```

不建议每次 run 都重建所有依赖，否则配置、日志、模型健康状态和工具状态会不稳定。

为什么要问：
这影响性能、状态共享和测试隔离。

你的回答：采取你的建议

---

### 问题 21：Runtime factory 是否需要支持依赖注入，用于测试 fake model / fake tool / temp SQLite？

通俗解释：
测试时不能总用真实模型、真实工具和正式数据库。

建议：
需要支持。factory 应允许传入：

```text
model_manager
tool_manager
session_manager
memory_adapter
react_agent
workspace_root
config
```

默认生产路径自动创建；测试路径可以注入 fake。

为什么要问：
这决定 Runtime 是否可测试。

你的回答：采取你的建议，测试和验收Runtime/cli/api层的时候可以按照这个来做，但是后续agent整体测试的时候我还是会使用真实的模型、真实工具和正式数据库的。

### 问题 22：Runtime 是否需要在启动时执行恢复逻辑？

通俗解释：
如果上次程序崩溃，SQLite 中可能有 running/waiting_user 的 run。

建议：
Runtime 初始化时调用：

```python

```

将 `pending / running / waiting_user` 标记为 `interrupted`。

为什么要问：
这能避免旧 run 永远卡在 running。

你的回答：采取你的建议

### 问题 27：第一版端到端测试需要覆盖哪些场景？

通俗解释：
Runtime 作为入口层，必须证明跨层真的能协作。

建议：
至少覆盖：

```text
1. 新 session 普通对话。
2. 指定 session 多轮对话。
3. 可见事件进入 timeline。
4. 内部事件不进入 timeline。
5. CLI chat 单轮。
6. CLI sessions / timeline。
7. API 创建 session。
8. API 发起 run。
9. WebSocket 推送 event 和 result。
10. waiting_user / pending_confirmation。
11. blocked_by_policy。
12. Memory 持久化失败 warning。
```

为什么要问：
这会成为开发完成后的验收矩阵。

你的回答：采取你的建议

```text
Runtime / CLI / API 架构设计文档

跨层联调验收
```
