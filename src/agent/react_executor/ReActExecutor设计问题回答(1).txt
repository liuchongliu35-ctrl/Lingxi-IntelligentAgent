# ReActExecutor 设计问题回答（1）

本文档用于第一轮确认 ReActExecutor 层设计问题。请直接在每个“你的回答：”后面填写答案。

说明：
- 这些问题不是考试题，目的是把 ReActExecutor V1 的边界、状态机、执行循环和开发步骤定清楚。
- ReActExecutor 必须和当前已经完成的 Analyzer V1、Planner V1 配合，不能重新承担 Analyzer 的自然语言理解职责，也不能破坏 Planner 已定义的 `TaskPlan -> TaskUnit -> PlanStep` 协议。
- 如果你不确定，可以写“按你的建议来”，我会按任务型 Agent 的常见工程做法给出保守方案。
- 有些问题后面写了“为什么要问”，方便你理解这个问题会影响哪部分设计。
- 如果本轮回答后仍有不明确的点，后续会继续生成 `ReActExecutor设计问题回答(2).txt`、`ReActExecutor设计问题回答(3).txt` 等。

重要概念修正：

标准 ReAct 的核心循环是：

```text
Thought -> Action -> Observation -> Thought -> ...
```

本文档里之前写的：

```text
Reasoning -> Decision -> Tool/Model -> Observation -> Checker
```

不是要替代标准 ReAct，而是把标准 ReAct 做工程化拆分：

```text
Thought    ~= Reasoning
Action     ~= Decision + Tool/Model
Observation = Observation
Checker    = 工程增强节点，原始 ReAct 论文中没有
```

也就是说，ReActExecutor 不是固定顺序执行器，而是“Planner 引导的 ReAct 执行循环”。Planner 给的是初始计划和边界，ReActExecutor 在执行时根据 Observation 继续推理、选择动作、检查结果；如果发现 Planner 的后续步骤不合适，可以做局部调整、fallback，或发出重规划请求。

## 1. ReActExecutor 在整个 Agent 中的定位

### 问题 1：你是否同意 ReActExecutor 只负责“执行计划”，不重新做 Analyzer 和 Planner 的职责？

通俗解释：
Analyzer 已经负责理解用户意图、参数、风险和复杂度；Planner 已经负责生成 `TaskPlan / TaskUnit / PlanStep`。ReActExecutor 不应该重新识别用户意图，也不应该重新生成完整初始计划。

建议：
ReActExecutor V1 消费 Planner 的结构化计划，负责执行过程中的 Plan-guided ReAct 循环：

```text
Thought/Reasoning
  -> Action Selection/Decision
  -> Action Execution/Tool or Model
  -> Observation
  -> Checker
  -> next Thought/Reasoning
```

其中 Planner 的 `TaskPlan / TaskUnit / PlanStep` 是执行参考、约束和初始路线，不是死板脚本。

为什么要问：
这决定 ReActExecutor 是第三层执行引擎，还是会变成第二个 Planner。

你的回答：是的，这一层消费Planner层的结果，然后执行任务完成用户的需求


### 问题 2：ReActExecutor 是否替换当前 `Executor`，还是先并行新增一个 `ReActExecutor` 类？

通俗解释：
当前 `src/agent/executor.py` 里已有顺序执行器。现在可以直接改它，也可以新增 `react_executor.py`，等稳定后再切换主链路。

建议：
V1 先新增 `ReActExecutor`，保持旧 `Executor` 可用。等 ReActExecutor 测试稳定后，再让 `ReactAgent` 默认使用它。

为什么要问：
这影响改动风险和回归测试范围。

你的回答：反正原来的顺序执行器Executor在后续正常跑的时候不会使用到所以删掉算了，完全使用ReActExecutor的react机制，既然确定了新的混合架构就不需要之前的顺序执行的架构了，简化开发复杂度嘛，后续没用的代码不需要


### 问题 3：ReActExecutor V1 的目标应该是哪一种 ReAct 执行粒度？

选项：

```text
A. 顺序执行增强：基本按 PlanStep 执行，只加 Observation、Checker、重试、日志
B. Plan-guided Step ReAct：以 PlanStep 为参考，每一步执行前后都由 LLM 推理和决策
C. TaskUnit ReAct：在一个 TaskUnit 内允许多轮 Thought/Action/Observation，并可局部调整后续步骤
D. 全局 ReAct：整个 TaskPlan 只作为参考，执行器完全动态决定下一步
```

建议：
V1 建议做 B，并吸收一部分 C 的能力：

```text
以 Planner 的 PlanStep 为主线
每个执行循环都调用 LLM Reasoning
允许在当前 TaskUnit 内做局部调整、重试、fallback
如果需要大范围改计划，则输出 request_replan，不在 V1 自动重写整个 TaskPlan
```

为什么要问：
这决定第一版是“死板按计划跑”，还是“按计划引导、执行时智能调整”。Planner 层已经给出了结构化初始计划，但 ReActExecutor 应该能根据 Observation 修正具体执行动作。

你的回答：按你的建议来，Planner动态重规划是后续V2做的

## 2. ReAct 循环粒度与状态机

### 问题 4：每个 PlanStep 是否都需要经过 Reasoning 节点？

通俗解释：
即使 Planner 已经给了步骤，执行前是否还要让 ReActExecutor 判断：

```text
这个步骤现在能不能执行？
依赖输入是否齐全？
是否需要确认？
应该调用工具还是模型？
```

建议：
需要。结合你的回答，V1 应该默认调用 LLM 做 Reasoning，但在调用 LLM 前仍需要先做确定性的工程检查：

```text
plan.can_execute 是否允许
依赖输入是否存在
是否命中危险动作
是否需要确认
是否超过最大循环次数
```

这些确定性检查不是替代 Thought，而是安全护栏。通过检查后，再让 LLM 基于 Planner 当前步骤、已有 Observation 和历史上下文进行 Thought/Reasoning。

为什么要问：
这决定 ReActExecutor 的“Reasoning”是工程状态判断，还是每步都消耗模型 token。

你的回答：需要，V1就设计为调用LLM吧，毕竟主要还是靠模型这个大脑来指挥和判断灵活处理的，万一规则不行那就完了
毕竟Reasoning也是react架构的一个步骤，
Thought（推理） -> Action（行动） -> Observation（观察）。这是react架构的标准流程
我的执行器ReActExecutor流程中：
Reasoning 对应 Thought。
Decision + Tool 共同对应 Action（Decision负责判断“是调用工具还是结束”，Tool负责执行具体动作）。
Observation 完全对应。
Checker 在原始论文中不存在，属于工程增强。
所以既然Reasoning 是推理这个步骤所以是比较重要的，是在处理一个任务的时候比如说到了第2步了，那么Reasoning 就需要知道第一步的结果然后让模型这个大脑根据已有情况判断下一步的Decision + Tool这个是什么样的，比如该做什么样的判断，第二步该调用什么工具，第一步已经完成到什么程度了第二步需要完成什么等等都需要这一步调用大模型大脑进行推理这样的agent才有意义，才是真正的agent自动规划实现步骤自动检测自动调整
在完成一个任务的时候大致流程如下：
Reasoning（分析现状）
→ Decision（判断：需要查资料）
→ Tool（执行查资料，得到原始结果）
→ Observation（将原始结果转译为自然语言状态）
→ Checker（检查：步数未超限，上下文未满，继续）
→ （回到 Reasoning）
...
→ 直到 Decision 输出“结束”
→ Checker（检查通过）
→ 输出最终答案。
其实这里显得Planner层做的步骤规划就有点死了，毕竟执行器需要根据实际的上一步执行情况来调整后面的步骤规划，所以Planner层就算是当做一个参考吧，先按照Planner层的规划跑，在推理时发现Planner层规划不对就做及时的调整吧，目前只能这样了


### 问题 5：Decision Branch 需要支持哪些 Action 类型？

建议 V1 支持：

```text
call_tool
call_model
ask_user
skip_step
retry_step
fallback_to_model
fallback_to_tool
request_replan
stop_success
stop_failed
blocked
```

通俗解释：
执行器每一轮 Thought 后都要选择一个 Action。`Decision + Tool/Model` 合起来才是标准 ReAct 里的 Action。

建议：
Action 类型先固定为枚举，LLM 必须从枚举里选择。不要让 LLM 在运行时自由发明新的 Action 类型；如果模型认为枚举不够，可以输出：

```text
request_replan
```

或在日志里记录 `unsupported_action_suggestion`，后续人工评估是否扩展枚举。

你的回答：这里的决策类型是固定死的吗，如果是的那就先固定死吧，到Reasoning节点进行推理的时候带这些固定死的，这样大模型就可以从这里面选择一个，如果这些固定死的不够，那就让大模型新增，灵活的去做
那你在开发的时候就尽量把所有的情况就是一般的agent处理任务时可能的判断全部枚举出来吧，目前只能这样了，你建议里面的那几个可能都不够，后续设计开发的时候尽量多考虑一些吧


### 问题 6：ReActExecutor 是否需要显式维护执行状态枚举？

建议状态：

```text
pending
running
waiting_user
completed
failed
skipped
blocked
cancelled
```

通俗解释：
`TaskUnit`、`PlanStep` 和整个执行结果都需要状态，否则后续日志、UI 和断点续跑都很难做。

你的回答：需要


### 问题 7：V1 是否需要支持暂停后继续执行？

例子：

```text
执行到 delete_file，需要用户确认
执行器暂停
用户回复“确认”
执行器从原步骤继续
```

建议：
V1 可以先不做完整断点续跑，但需要预留 `waiting_user` 状态和 `pending_confirmation` 记录。真正多轮恢复放到 V2。

为什么要问：
这影响确认机制、会话状态保存和 ReactAgent 主链路。

你的回答：这个应该需要吧，而且你举的例子不妥当那个吧，这里确认是否删除和断点继续执行有什么关系呢，这里确认流程不是代码层面上停止流程吗，if判断是否确认后继续后续的流程不是吗，这不涉及断点啊，这里用户确认后根据用户选择继续后续的流程不涉及断点重续吧，什么是断点呢，断点是agent正常跑的时候（没有任何需要用户确认的提示）手动点击了停止，导致对话停止，这个断点续跑一般的agent没办法实现吧，就我使用的trae和codex都没有这个功能，点击停止后就没有办法在后续继续上一个对话没有完成的，不过在后续的对话中如果提到了继续上一个对话没有完成的大模型确实可以识别出上一个对话完成到哪里了，这个应该需要做，所以还是需要记录一下每一个对话完成的进度的，方便如果误触暂停了，下一个对话还是可以根据上一个对话（或者前面对话）判断出任务已经实现到哪里了，也知道后面还有哪些没有实现

## 3. TaskPlan / TaskUnit / PlanStep 的消费方式
这三个概念的理解：
TaskPlan
  = 一次用户请求对应的整体执行计划

TaskUnit
  = TaskPlan 里的一个子任务单元
  = 可能对应一个 intent，也可能由多个强依赖 intent 合成

PlanStep
  = TaskUnit 里的具体执行步骤
  = 真正给 ReActExecutor 执行时消费的最小计划单位
  
### 问题 8：ReActExecutor 是否严格按 `task_units` 顺序执行？

通俗解释：
Planner 已经把任务分成多个 TaskUnit。V1 是严格按顺序执行，还是允许 ReActExecutor 根据 Observation 做局部调整？

建议：
V1 默认按 `task_units` 顺序执行，但不是死板执行：

```text
1. TaskUnit 外层顺序默认遵守 Planner。
2. TaskUnit 内部可以根据 depends_on/input_from 和 Observation 做局部调整。
3. 如果 LLM Reasoning 判断当前 TaskUnit 顺序明显不合理，可以跳过、重试、fallback，或输出 request_replan。
4. V1 不做跨 TaskUnit 并行，也不自动重写整个 TaskPlan。
```

为什么要问：
这可以同时保留 Planner 的结构化控制，又让 ReActExecutor 具备真正的 ReAct 执行灵活性。

你的回答：按你的建议来


### 问题 9：ReActExecutor 执行步骤时以 `plan.steps` 扁平列表为主，还是以 `task_units.step_ids` 为主？

通俗解释：
Planner 同时保留了 `task_units` 和扁平 `steps`。执行器需要明确以哪个为执行入口。

建议：
以 `task_units` 为外层顺序，每个 TaskUnit 通过 `step_ids` 找到对应 `PlanStep`；如果缺少 `task_units`，再兼容 `plan.steps` 扁平顺序。

为什么要问：
这决定 ReActExecutor 是否真正消费 Planner 的三层结构。

你的回答：按你的建议来


### 问题 10：如果 `depends_on` 指向的前置步骤失败，当前步骤是否默认跳过？

建议：
默认跳过并标记 `skipped`，最终结果说明跳过原因。只有 `on_failure=skip_optional` 或步骤标记可选时，才允许继续后续无依赖步骤。

你的回答：这个不懂是哪个结构里面的字段，请在下一个问题询问文档中重新询问并详细讲一下


### 问题 11：如果 `input_from` 引用不存在，应该视为计划错误还是执行错误？

建议：
视为执行前校验错误，当前步骤不执行，并返回结构化失败。因为 Planner 已经做过计划校验，如果运行时仍出现，说明计划或状态被破坏。

你的回答：采取你的建议，就是在之前有需要校验一下，如果校验发现某个字段是空的或者值不对并会影响后续的执行那就需要返回结构化失败提示，不过这种错误后续V2应该做防范尽量做到出现这种情况的概率为0

## 5. Tool Node 与工具调用

### 问题 16：ReActExecutor 调用工具时是否必须统一通过 `ToolManager.run_tool()`？

建议：
V1 是。ReActExecutor 不直接调用具体工具类，统一走 `ToolManager` 或未来 `ToolRegistry`。

为什么要问：
这保持工具层边界清晰，也方便后续统一 schema、安全和日志。

你的回答：采取你的建议，就是工具层统一对外提供接口，ReActExecutor调用工具接口，传指定参数即可，这样也是工程化保持边界清晰的需求


### 问题 17：工具调用前是否需要再次做安全检查？

通俗解释：
Analyzer 和 Planner 已经做了风险判断，但执行器是最后一道防线。执行前是否还要检查：

```text
是否写工作区外文件
是否删除文件
是否执行代码
是否调用 shell
是否访问敏感路径
```

建议：
必须做。Analyzer/Planner 是前置判断，ReActExecutor 是执行前拦截。

你的回答：需要，这种工程化的安全措施是必须的


### 问题 18：如果工具返回 `ToolResult.success=False`，ReActExecutor 是否应该先按 `ToolResult.code` 分类处理？

建议：
是。比如：

```text
missing_config -> ask_user 或 fallback
missing_argument -> failed 或 ask_user
permission_denied -> blocked
timeout -> retry
tool_not_found -> fallback_to_model 或 missing_tools
```

为什么要问：
这决定失败处理是结构化决策，还是简单返回错误文本。

你的回答：采取你的建议


### 问题 19：工具参数是否只使用 Planner 已装配好的 `step.args`，还是 ReActExecutor 可以补参数？

建议：
ReActExecutor 可以做运行时参数注入，例如把 `input_from` 的 Observation 输出注入到 `text/content`，但不重新理解用户意图来发明关键参数。

你的回答：采取你的建议，就是调用工具需要传入的参数一般都是固定的那几个，只不过那几个参数的具体值是在ReActExecutor运行时得到的这样就动态注入，发明新入参明显是不行的，其实后续添加工具mcp时应该一般的mcp工具都是约定好入参的，所以只需要将新加入的mcp需要的入参列表导入到内部即，让大模型知道这个工具需要的入参，不过应该需要运行时导入的参数一般比较少，一般的参数使用默认的即可了，就比如那5个基础工具基本入参都是确定的，也就只有2到3个参数是需要动态传的，这个是不是需要做一个协议，就是每一个工具需要的入参整个系统是知道的，这部分是固定流程化的，写死的


### 问题 20：如果工具参数仍缺失，ReActExecutor 应该询问用户还是直接失败？

建议：
如果缺的是用户必须提供的信息，进入 `ask_user`；如果缺的是 Planner 应该生成的内部参数，标记计划错误并失败。

你的回答：我觉得工具调用时需要的入参应该固定好，就那几个字段整个系统都是知道的，最后可能会出现问题的就是上游给不了这个工具需要的这个参数，就是说这个参数值为空，这样的话还是跳过正常进行下一步吧，但是在给用户的反馈文字中需要标明这一步可能是失败的，如果不影响完成后续的任务和步骤那么后续的步骤和任务最好还是正常行去完成

## 6. Model Node 与模型调用

### 问题 21：`step_type=model/respond` 是否统一调用 `ModelManager.generate()`？

建议：
V1 是。后续再扩展流式输出、多模型路由、结构化响应。

你的回答：V1就做流式输出吧，最好用户可以看到流式的思考内容以及每一步骤的完成情况，不过调用模型时可以显示思考，用户界面点击思考就可以看到模型输流式输出内容或者，然后具体调用工具或者命令行执行时的日志用户界面也可以点击展开看到工具调用日志和调用运行结果就和codex这样

## 7. Checker 节点与完成判断

### 问题 25：每轮 Action/Observation 后是否都需要 Checker 判断？

建议：
需要。Checker 是工程增强节点，不属于原始 ReAct 的必要定义，但对工程化 Agent 很重要。它判断：

```text
是否成功
输出是否为空
是否满足 expected_output
是否需要重试
是否需要 fallback
是否需要询问用户
是否可以进入下一步
是否需要 request_replan
是否达到终止条件
```

通俗解释：
原始 ReAct 可以让模型自己根据 Observation 继续 Thought，但工程实现里需要 Checker 兜底判断，防止无限循环、误执行、空结果继续传递。

你的回答：需要，采取你的建议


### 问题 26：Checker V1 主要使用规则判断，还是调用 LLM 判断？

V1 建议采用“规则底线 + LLM 辅助”：

```text
规则 Checker 负责硬约束：
  超时、失败码、空输出、最大循环次数、安全策略、依赖缺失

LLM Checker 负责语义判断：
  当前 Observation 是否满足 step.expected_output
  是否需要继续查找信息
  是否应该 fallback
  是否需要 request_replan
```

为什么要问：
LLM Checker 灵活但不稳定，规则 Checker 可测试。两者结合更适合你的“模型作为大脑，但工程可控”的目标。
