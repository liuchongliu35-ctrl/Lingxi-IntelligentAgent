# ReActExecutor 设计问题回答（2）

本文档用于第二轮确认 ReActExecutor 的“模型交互协议”和“结构化数据设计”。请直接在每个“你的回答：”后面填写答案。

说明：
- 本轮只问 ReActExecutor 和模型大脑如何交互，不再重复问 Planner / Analyzer 的边界。
- 根据 ReAct 论文，核心是 `Thought -> Action -> Observation` 的交替循环；根据当前工具调用和 Structured Outputs 的工程实践，模型输出最好是结构化的，而不是混在一段自然语言里。
- 也就是说，ReActExecutor 里最重要的是“模型应该输出什么结构，执行器应该怎么消费它”。
- 如果本轮回答后还有不清楚的点，我会继续出 `ReActExecutor设计问题回答(3).txt`。

## 1. 模型输出协议

### 问题 1：你是否同意 ReActExecutor 的模型输出应该是“结构化对象”为主，而不是一大段自由文本？

通俗解释：
模型每一轮不应该一边写思考、一边写动作、一边写给用户看的回答混在一起。更稳妥的方式是模型返回一个结构化对象，让执行器按字段消费。

建议：
V1 采用结构化输出优先。自由文本只作为少量 `user_message` 或 `reasoning_summary` 的补充。

你的回答：同意，采取你的建议


### 问题 2：你是否同意把模型输出分成几个明确字段？

建议字段示例：

```text
reasoning_summary
action_type
action_target
action_args
user_message
expected_observation
confidence
needs_replan
final_answer
```

通俗解释：
这样可以把“模型在想什么”“模型要执行什么”“模型要对用户说什么”分开。

你的回答：确定，需要区分开来，这样就是结构化的核心目标，所以在设计的时候需要尽量考虑好所有情况这样设计字段就全面，你给出的示例可能不全哦


### 问题 3：你是否接受“完整思考内容不直接暴露，只记录摘要”的设计？

通俗解释：
你前面的回答里已经提到，太长的思考文本只记摘要。这里需要正式确认：是否只保留短摘要，不保存完整自由思维链。

建议：
V1 只保存 `reasoning_summary` 或 `thought_summary`，不把长篇自由推理当成正式协议字段。

为什么要问：
这会影响日志体积、调试方式和模型输出协议。

你的回答：可以在用户交互界面流式输出出来，用户对话可以直接存档，还是保存下来吧保存到数据库中，这样用户还可以看到历史对话记录，还是不要做摘要了，毕竟摘要也需要消耗token嘛


### 问题 4：模型是否必须输出严格 JSON / 结构化 schema？

建议：
需要。尽量参考 Structured Outputs / strict schema 的方式，让模型输出可以被校验、反序列化和自动重试。

你的回答：需要，采取你的建议


### 问题 5：模型输出 schema 是否固定为一种“ActionPacket”？

选项：

```text
A. 固定单一 ActionPacket
B. 根据 action_type 使用不同子 schema
C. 先用通用 JSON，后续再细分
```

建议：
V1 选 A 或 B，不建议继续靠通用自然语言拼接。

你的回答：采取你的建议

## 2. Thought / Action / Observation 的分层

### 问题 6：你是否同意把 Thought 设计成“内部推理摘要”，而不是用户可见内容？

通俗解释：
Thought 是模型在执行某一步时的内部判断摘要，给执行器和日志看，不直接当用户回复。

建议：
`thought_summary` 只要简短、可追踪即可。

你的回答：反正直接给用户看的有两种：1、执行过程（*比如编辑了那个文件，修改添加了哪些内容，然后执行了什么命令，执行结果是什么，调用了那个mcp工具，调用结果是什么）2、每一步执行前的思考计划（比如下一步打算向a.py文件实现某个功能，那就先使用人可以看的流畅的文字描述下一步计划怎么做，然后再执行这一步操作如下面这个例子）
例子：“我先读你已经填写的回答，重点看你对 ReAct 定义和这条 Reasoning -> Decision -> Tool -> Observation -> Checker 链路的疑问在哪里，再判断是问题文档需要改，还是架构表述需要收敛。

你指出的问题是对的：我上一版问题把 ReAct 拆成了工程节点，但没有先把“标准 ReAct”和“工程增强 ReAct”的关系讲清楚，容易让人误解成一种固定流水线。这里需要先校准概念，再继续问细节。
我会在现有问题文件里直接做一次“概念校准”修改，保留你已经写的回答，不覆盖你的内容。重点改前面容易误导的几个问题和说明，把它从“固定顺序执行器增强”调整成“Planner 引导的 ReAct 执行循环”。

Edited ReActExecutor设计问题回答(1).txt+71-13（这个就是执行的过程，这个后续用户可以点开查看详细执行结果，比如修改了哪些内容）

### 问题 7：你是否同意 Action 只负责“选择动作”，不负责长篇说明？

建议：
Action 只输出：

```text
call_tool / call_model / ask_user / retry / fallback / finish / request_replan
```

再附带必要参数。

通俗解释：
这样能把“模型决定做什么”和“模型解释为什么这么做”分开。

你的回答：需要，确实需要分开明确界限，不是一个东西就不要混在一起，每个节点做的事情需要专一


### 问题 8：Observation 是否应该由执行器统一生成，而不是由模型自己编造？

建议：
是。Observation 应来自真实工具、真实模型响应或真实执行结果，由执行器记录和归一化，不让模型自己伪造。

你的回答：那肯定是把执行结果给模型进行整理啊，后续react循环的下一轮的Reasoning节点推理还需要上一步的观察结果在进行推理呢


### 问题 9：Observation 是否要分成“原始结果”和“摘要结果”两层？

建议：
需要。比如：

```text
raw_observation: 工具原始返回
observation_summary: 给模型下一轮看的摘要
```

通俗解释：
原始结果便于调试，摘要结果便于下一轮推理和控制上下文长度。

你的回答：不能说摘要，摘要可能会比较简短导致可能会漏掉关键信息，所以还是模型整理原始结果输出二次可以由下一轮模型可以消费的信息，最主要的是不能将关键信息遗漏掉，尽量保留所有信息


### 问题 10：用户可见文本和执行器内部文本是否必须分离？

建议：
必须分离。比如：

```text
user_message: 给用户看的话
action_args: 给执行器的参数
reasoning_summary: 给执行器和日志看的摘要
```

为什么要问：
这会直接决定模型输出结构是否清晰。

你的回答：需要分离，执行器里面的叫日志，会有一些什么变量啊啥的，但是给用户看的就需要实地自然语言大模型生成的对当前状况进行整理后的描述（比如在执行下一个步骤前说明下一步计划怎么做，就像前面我提到的那个例子那样，最后总结做了什么等等）

## 3. Action 类型与执行含义

### 问题 11：你是否同意 Action 类型继续保持固定枚举？

建议枚举：

```text
call_tool
call_model
ask_user
retry
fallback_to_model
fallback_to_tool
finish
request_replan
blocked
```

通俗解释：
这和你前面同意“先固定死，再看是否扩展”是一致的。

你的回答：先枚举吧，反正这种东西还是需要后续设计开发测试的过程中补充的，不过你在设计的时候尽量去拓展多考虑一些边界情况，尽量将所有可能的情况都考虑到


### 问题 12：`call_model` 和 `finish` 这两个动作是否要区分？

建议：
要区分。

```text
call_model = 让模型继续生成一个中间步骤结果
finish = 结束当前任务并生成最终回答
```

你的回答：需要，一个是中间结果，一个是结尾结果，不是一个东西


### 问题 13：`ask_user` 是否要区分“补参数”和“确认危险动作”？

建议：
要区分，至少通过字段区分：

```text
ask_type = missing_info | confirmation
```

你的回答：需要，向用户确认的问题类型还是需要做一下区分的，设计的时候多考虑一些可能会出现的类型


### 问题 14：`request_replan` 是否是 V1 允许的标准动作？

建议：
允许。它表示当前计划和实际执行偏差过大，需要 Planner 或更高层重新规划，但 ReActExecutor 自己不重写整个 TaskPlan。

你的回答：采取你的建议

## 4. 模型和执行器的消息往返

### 问题 15：你是否同意 ReActExecutor 每一轮都按“模型输出 -> 执行动作 -> 回填 Observation -> 再调用模型”的方式往返？

通俗解释：
这就是标准 ReAct 的核心闭环。

建议：
是。每一轮模型都要看到上一步的 Observation，再决定下一步 Action。

你的回答：采取你的建议，大致就是这样的流程，反正按照react结构做就行了，再补一些工程化的东西兜底就行了


### 问题 16：模型下一轮输入是否应包含以下内容？

建议至少包含：

```text
用户输入
当前 TaskPlan / 当前 TaskUnit / 当前 PlanStep
上一轮 thought_summary
上一轮 action
上一轮 observation_summary
历史必要上下文
安全约束
可选动作枚举
```

你的回答：采取你的建议，设计的时候就需要尽量多加一些了，毕竟以防万一嘛，万一多一些信息后续做出的决策就要更正确一些呢


### 问题 17：你是否同意每一轮都控制上下文长度，只保留必要摘要？

建议：
是。长任务里不能把全部历史原样塞回模型，否则上下文会很快膨胀。

你的回答：需要，给模型的prompt需要控制长度，之前的信息只需要将关键信息给后面，注意关键信息，可以让模型将关键信息或者将所有信息以结构化的形式留给后续的模型作为prompt，毕竟结构化的东西信息强，需要的文字还少


### 问题 18：模型如果输出不符合 schema，执行器应该怎么处理？

建议选项：

```text
A. 立即失败
B. 重试一次并修复 prompt
C. 退回到 ask_user 或 fallback_to_model
```

建议：
V1 可以用 B + C 的组合。

你的回答：采取你的建议，反正调整/重试是大方向，但是重试还是有次数限制的，5次最多了


### 问题 19：模型是否允许输出“当前这一步不做动作，只给出推理摘要”？

通俗解释：
有些回合模型可能只需要思考，不立即调用工具。

建议：
可以，但要把它显式编码成某种 Action，例如：

```text
call_model
```

或一个更细的 `reason_only`。

你的回答：可以，这个情况是肯定会出现的

## 6. V1 开发边界

### 问题 23：你是否认可 ReActExecutor V1 先把“结构化交互协议”做稳，再追求更强的动态能力？

建议：
先做稳：

```text
结构化输出
Action 枚举
Observation 归一化
Checker
重试 / fallback
```

再逐步增强动态重规划。

你的回答：是的，先让模型可以正常指挥工作，先可以把工作做完，至于优化后续再说


### 问题 24：你是否希望 ReActExecutor V1 先支持下面这三个最核心的数据结构？

建议：

```text
ThoughtPacket
ActionPacket
ObservationPacket
```

如果你愿意，也可以换成你更喜欢的命名，比如：

```text
ExecutionThought
ExecutionAction
ExecutionObservation
```

你的回答：ThoughtPacket
ActionPacket
ObservationPacket这三个就可以

比如可以叫：

```text
ReActStep
ExecutorPacket
ActionPacket
ExecutionTurn
```

建议：
先统一一个名字，后续实现和日志都会更清楚。
