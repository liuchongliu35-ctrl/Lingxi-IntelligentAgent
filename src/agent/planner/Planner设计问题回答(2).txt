# Planner 设计问题回答（2）：ReAct 架构与规划循环确认

本文档用于第二轮确认 Planner 是否按 ReAct / Plan-and-Execute / 混合架构设计。

背景：
你在第一轮回答中提到，希望 Agent 像 Codex、Trae 一样具备“大模型作为大脑”的能力，而不是只靠大量固定规则。你也提到任务执行可能需要反复经过：

```text
Reasoning Node -> Decision Branch -> Tool Node -> Checker
```

所以这一轮重点确认：Planner、Executor、Reasoning、Checker 之间到底如何分工。

---

## 1. 当前架构是否要升级成 ReAct 混合架构？

### 问题 1：你是否希望最终架构是“Analyzer + Planner + ReAct Executor”的混合架构？

通俗解释：
当前代码更像：

```text
Analyzer -> Planner -> Executor
```

而真正 ReAct 更像：

```text
Reason -> Decide -> Act -> Observe -> Check -> Reason ...
```

建议采用混合架构：

```text
Analyzer
  -> Planner 生成初始计划
  -> Executor 按计划执行
      -> Reasoning Node 判断当前状态
      -> Decision Branch 决定调用工具/继续思考/结束/请求用户
      -> Tool Node 执行工具
      -> Checker 判断是否完成或是否继续
```

这样 Analyzer/Planner 保持工程化可控，同时 Executor 内部具备 ReAct 循环能力。

你的回答：可以这样做，前提是这样做确实可以保证agent具备比较强的自主处理问题的能力，这个架构设计需要符合agent的设计理念，核心就是这个Executor执行层，执行层采取react的架构来实现任务的处理和完成


### 问题 2：Planner 是只生成“初始计划”，还是每一步执行后都重新参与规划？

选项：

```text
A. Planner 只生成初始计划，Executor 内部循环执行和检查
B. 每一步执行后都回到 Planner 重新规划
C. V1 先 A，V2 再支持失败后的局部重规划
```

建议：
选 C。V1 先让 Planner 生成稳定初始计划；Executor 执行失败时可根据 Planner 给的 `on_failure` 策略处理。V2 再做动态重规划。

你的回答：采取你的建议，动态重规划V2再完成这个功能


### 问题 3：大模型“思考”节点放在哪里？

选项：

```text
A. 放在 Planner：让 LLM 生成完整 TaskPlan
B. 放在 Executor：每一步执行前/后让 LLM 判断下一步
C. 两边都有：Planner 用 LLM 生成计划，Executor 用 LLM 做执行过程中的 Reasoning
```

建议：
V1 可以两边都有，但要分清职责：

```text
Planner LLM：生成结构化计划
Executor LLM：根据执行结果判断下一步或生成模型回答
```

你的回答：Planner和Executor都需要去调用模型层的接口，使用agent的大脑，Analyzer里面不是也有一个大模型兜底的意图识别方案吗，那里也需要调用模型层，然后处理每一步时的思考过程需要再日志打印出来

## 2. Planner 生成计划：规则还是 LLM？

### 问题 4：Planner V1 是否采用“规则优先 + LLM 兜底”的计划生成方式？

通俗解释：
常见任务用规则，复杂任务交给大模型规划。

建议：

```text
1. 特殊策略先处理：block / clarify / confirm / missing_tools / chat
2. 简单 micro 任务走规则模板
3. 常见多意图组合走规则模板
4. 复杂软件工程、多步骤开放任务走 LLM Planner
5. LLM Planner 必须返回结构化 JSON，再校验后才能进入 Executor
```

你的回答：对，规则过滤一部分，规则无法处理的就使用大模型处理，所以规则的设定也需要尽量细致一些，不要出现明明是复杂任务却被规则过滤出来导致按照简单任务处理了


### 问题 5：LLM 生成的计划是否必须经过规则校验？

通俗解释：
大模型可能生成不存在的工具、危险步骤、缺参数步骤，所以不能直接信任。

建议：
必须校验。至少校验：

```text
工具是否存在
危险动作是否需要确认
步骤字段是否完整
是否引用了不存在的上游步骤
是否越过 Analyzer 的 block/confirm 策略
```

你的回答：需要校验，先就校验你的建议里面的这几个吧。反正确保最后可以正常跑就行了


### 问题 6：如果 LLM 计划校验失败，应该怎么处理？

选项：

```text
A. 直接失败，提示无法生成可靠计划
B. 回退到规则计划
C. 让 LLM 重新生成，最多重试 N 次
D. 先重试，再回退规则，再失败
```

建议：
选 D，最多重试 2 次。Planner 只负责“重新生成计划”，不执行工具。

你的回答：D，先重试3次，让大模型调整方案，其实比如第一次就显示工具不存在，这样情况第二次重试就直接生成命令行的解决方案就行了，一般大多数都是这种工具缺失的问题，命令行可以作为工具缺失兜底方案
当然需要注册工具列表然后告诉我本地有哪些mcp工具，然后每个工具如果调用，这样大模型就可以提前知道是否可以使用某一个工具来解决了，如果工具列表里面不存在自然就不会将不存在的工具放到计划步骤里面

## 3. ReAct 循环由谁负责？

### 问题 7：Executor 是否应该升级为 ReActExecutor？

通俗解释：
现在 Executor 是顺序执行计划。ReActExecutor 则会在执行过程中循环：

```text
看当前状态 -> 思考 -> 决策 -> 调工具 -> 观察结果 -> 检查是否完成
```

建议：
V1 可以保留 `Executor` 名称，但内部逐步引入 ReAct 组件：

```text
ReasoningResult
DecisionResult
Observation
CheckResult
ExecutionState
```

你的回答：需要升级为ReActExecutor


### 问题 8：Reasoning Node 是否每一步都必须调用大模型？

选项：

```text
A. 每一步都调用，更像 ReAct，但成本高
B. 只有 model_only、复杂步骤、工具失败后才调用
C. V1 规则执行为主，必要时调用
```

建议：
选 B 或 C。否则简单计算、读文件也调用大模型，会慢且浪费。

你的回答：B，这里可以给简单任务标签，通过标签来区别对待简单任务和复杂任务，可以分多一些复杂度层次，然后按照情况来判断是否需要调用大模型来处理


### 问题 9：Decision Branch 允许哪些决策？

建议 V1 支持：

```text
call_tool
call_model
ask_user
finish
retry
fallback_to_shell
fail
```

通俗解释：
这些决策对应“调用工具、调用模型、问用户、结束、重试、命令行兜底、失败”。

你的回答：采取你的建议


### 问题 10：Checker 如何判断任务结束？

建议 V1 使用几类判断：

```text
所有计划步骤完成 -> finish
当前步骤失败且超过重试次数 -> fail
缺少用户输入 -> ask_user
工具返回结果满足 expected_output -> 继续下一步或 finish
危险动作未确认 -> pause
```

你的回答：采取你的建议，还有设计的时候尽量多思考一些边缘情况然后补充进去

## 4. 工具失败后的命令行兜底

### 问题 11：你是否确认 V1 要支持“工具失败后尝试命令行兜底”？

通俗解释：
例如专门的 `file_move` 工具不存在，但可以用命令行移动文件。

风险：
命令行能力很强，也很危险。必须限制白名单动作，不能让模型随便生成任意命令。

建议：
V1 可以预留 `fallback_to_shell` 决策，但只允许低风险命令：

```text
列目录
读取文件
创建目录
复制文件
移动工作区内文件
运行测试命令
```

不允许：

```text
删除文件
系统目录操作
安装/卸载软件
格式化磁盘
修改权限
执行不明脚本
```

你的回答：这个提交给用户决定吧，用户可以选择solo权限，这样不管什么命令他都会执行，可以选择每次执行一个命令都要询问用户，就像codex这样，没执行一个命令都会询问用户是否执行


### 问题 12：命令行兜底命令是否必须经过安全校验？

建议：
必须。并且命令执行前要由 ShellTool/CommandTool 做工作区限制、危险命令检测、超时限制。

你的回答：采取你的建议


### 问题 13：执行代码和执行命令是否都需要用户确认？

背景：
你之前确认 `execute_code` 需要确认，但又希望命令行作为基础工具。

建议：
区分：

```text
安全只读命令：可默认执行，例如列目录、查看文件
写入/移动/测试命令：可按配置执行
删除/危险/系统命令：必须确认或直接 block
```

你的回答：采取你的建议，执行代码（比如他给我生成了一个python脚本然后需要问我是否需要执行这个脚本，如果确定那就去执行这个脚本，至于如何执行我是本质还是命令行去命令行里面调用python命令去执行脚本）

## 5. Planner V1 边界重新确认

### 问题 14：根据第一轮回答，Planner V1 是否应该这样定义？

建议：

```text
Planner V1 = 规则模板 + LLM 规划兜底 + 结构化计划校验 + 日志 + 测试

不负责：
- 真正执行工具
- 真正重试
- 真正动态重规划
- 精确代码 patch
- 长任务调度

预留：
- ReAct Executor 所需字段
- retry / fallback_to_shell / ask_user / finish 等决策字段
- 步骤依赖和中间结果传递
```

你的回答：采取你的建议


### 问题 15：你是否接受当前项目不是“纯 ReAct”，而是“任务型 Agent + ReAct 执行循环”的工程化架构？

通俗解释：
纯 ReAct 通常是模型每轮自己决定下一步做什么；你的项目还有 Analyzer 和 Planner，这让系统更可控。

建议：
面试时可以这样讲：

```text
这个 Agent 不是裸 ReAct，而是 Analyzer/Planner/Executor 分层架构。
Analyzer 负责任务理解，Planner 负责生成结构化计划，Executor 内部可以采用 ReAct 循环完成 Reason-Act-Observe-Check。
这样既保留 ReAct 的动态执行能力，又避免完全依赖模型自由发挥。
```

你的回答：接受，这样显得我思考过结果改良后的工程化架构，不是没有思考做的纯react,复合结构更加高级一些
