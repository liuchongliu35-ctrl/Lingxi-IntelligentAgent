## 1. 上下文压缩与记忆联动

### 问题 1：Session 级上下文压缩到底由谁发起、由谁执行、由谁保存？

通俗解释：
你已经明确上下文压缩很重要，而且会联动 Memory / Planner / ReActExecutor / Models 多处。现在还需要确认的是：到底是谁判断“该压缩了”，谁真正生成压缩结果，谁把结果写回会话或记忆层。

建议：
V1 先明确分工：

```text
触发判断：
  Analyzer / Planner / ReActExecutor / Session 层根据长度阈值、轮次阈值、token 阈值决定是否触发压缩

压缩执行：
  Models 层提供 summary / compression route，负责生成结构化压缩结果

结果保存：
  Memory / Session 层负责写入会话摘要、历史压缩块或记忆索引
```

为什么要问：
这决定上下文压缩是 Models 层的一个能力，还是 Memory/Session 层的一个流程，避免后面在多个层里重复实现。

你的回答：采取你的建议，上下文压缩是 Models 层的一个能力，至于什么时候需要调用 Models 层压缩接口，需要压缩多少东西，由其他层来做决定， Models 层只负责压缩返回压缩结果即可


### 问题 2：压缩结果应该保存成什么形式？

通俗解释：
压缩不能只是“生成一段摘要文本”这么简单。后面还要考虑能不能再喂回模型、能不能追踪来源、能不能和会话历史拼接。

建议：
至少要区分三类结果：

```text
short_summary:
  给模型回填的短摘要

compressed_chunks:
  被压缩前的原始信息索引或引用

compression_metadata:
  压缩触发原因、压缩轮次、原始长度、压缩后长度、是否丢失关键信息
```

为什么要问：
如果只存一段摘要，后续很难回溯原始信息，也不利于 Memory / RAG 联动。

你的回答：压缩后的文本不仅仅指返回一个str就行了，而是需要将压缩文本连同其他的一些信息形成结构化对象返回，反正这段压缩后的文本肯定是需要被其他层比如 Memory / RAG进行消费的，除了这段压缩文本时必须得以外可能还会需要其他的信息数据，所以需要哪些字段信息你来设计决定，反正只要其他层消费这个压缩结果时可以形成闭环处理逻辑足够完成整条记忆链路即可


### 问题 3：上下文压缩是否允许模型辅助压缩，还是必须有规则兜底？

通俗解释：
你前面说“这个压缩可以交由模型来做”。这里要进一步确认：模型压缩是主路径，还是只是一种辅助路径？如果模型压缩失败，是否有规则版兜底？

建议：
V1 采用双路径：

```text
主路径：
  由 Models 层或专门 compression route 调用模型压缩

兜底：
  规则化截断 + 保留关键字段 + 明确失败码
```

为什么要问：
纯模型压缩更灵活，但失败时容易让会话断裂；纯规则压缩又容易丢语义。

你的回答：模型压缩是主路径，规则化需要，主要是控制文本长度，有时候文本太长了就需要分段压缩然后整合，不然大模型有时候也处理不了太长的原文本，或者原文本太长导致压缩效果不好，所以需要规则做分段处理，规则做兜底吧，但是规则不能直接生成压缩的内容只是作为模型的兜底，做一些工程化预防措施，确保上层传过来的文本可以被有效压缩，当然传原文本的那个层也需要设计好什么时候进行一次压缩，一次压缩文本控制长度（包含几个对话，分几段压缩等等就算是压缩方案吧，所以压缩方案需要设计一下，这个应该是通用的功能所以交给Models 层来做吧，你说呢？）


## 2. 成本与观测边界

### 问题 4：Models V1 里 `cost` 字段到底保留还是只做可选元数据？

通俗解释：
你前面说成本估算暂时不需要，因为 provider 那边能看；但完成标准里又写了 `cost`。这两边需要统一一下。

建议：
V1 仍保留 `cost` 字段，但它是可选元数据：

```text
provider 返回或配置表可计算 -> 填 cost
provider 不提供 -> 置 None
```

这样不强依赖成本估算，但后续日志、观测、UI 仍有字段承接。

为什么要问：
如果完全不保留，后面 `logs/models.log`、告警、UI 面板和路由对比会少一个重要维度。

你的回答：采取你的建议

你的回答：需要，开发阶段暂时不启用，后续整体测试阶段就可以开启这个真实的模型 provider

## 4. 冷却、重试与错误分类

### 问题 7：fallback / 熔断 / retry 的错误分类是否需要更细的统一表？

通俗解释：
你已经认可需要细化冷却粒度，但现在还差一张统一规则表：什么错误重试，什么错误 fallback，什么错误直接冷却，什么错误绝不切换。

建议：
V1 先按下面维度统一：

```text
鉴权类:
  401 / 403 -> 冷却 credential_slug

模型缺失类:
  404 / model_not_found -> 冷却 provider_conf_id + model

限流类:
  429 / rate_limited -> retry + 视情况 fallback + 冷却当前候选

服务端类:
  5xx / timeout / network_error -> retry + fallback + 短冷却

请求语义类:
  invalid_prompt / schema_invalid / invalid_json -> 先 repair，不盲目 retry

安全阻断类:
  blocked_by_policy / forbidden / user_cancelled -> 不 retry，不 fallback
```

为什么要问：
没有统一表，后面每个 provider 的错误码和错误消息都会各自长一套，路由和日志都会乱。

你的回答：先采取你的建议吧，后续测试如果还发现有其他情况再处理


### 问题 8：模型厂商自定义错误码或错误消息是否要纳入冷却判断？

通俗解释：
有些 provider 不只返回标准 HTTP 状态码，还会返回自己的业务错误码或 message。这里要确认 Models 层是只看 HTTP 状态，还是也看业务错误码 / message / hint。

建议：
要纳入，但只作为辅助判断：

```text
优先级：
  HTTP status
  provider error_code
  provider error message / hint
  本地归一化错误码
```

为什么要问：
如果只看 HTTP 状态，很多 provider 的“鉴权失败 / 配额不足 / 模型不存在”会被误判。

你的回答：采取你的建议，模型自家的业务错误码作为辅助判断


## 5. 配置与标识

### 问题 9：`provider_conf_id` 和 `credential_slug` 是否都应该是稳定标识？

通俗解释：
后面要做路由、verify、日志、enable/disable、manage-models，标识体系必须统一。现在还要确认：哪些 ID 是稳定主键，哪些只是显示名。

建议：
```text
provider_conf_id:
  稳定主键，建议 UUID 或不可变唯一 id

credential_slug:
  在 provider_conf 内部稳定唯一，便于选用具体 key

display_name / alias:
  只做展示，不参与路由主键
```

为什么要问：
如果显示名和路由主键混用，后面改名会把配置、路由和日志全打乱。

你的回答：采取你的建议


### 问题 10：embedding provider 是否必须与 chat provider 完全分离配置？

通俗解释：
你前面已经同意 embedding 和 chat 路由完全分离，但还没最终定清：是完全独立的 ProviderConf，还是共享一部分 provider 资源但路由分开。

建议：
V1 倾向完全分离：

```text
chat route:
  DEFAULT_CHAT_MODEL

embedding route:
  DEFAULT_EMBEDDING_MODEL
```

同一个 provider 也可以同时承担 chat / embedding，但配置和路由应该分开。

为什么要问：
这会影响后面 Memory / RAG 和 Models 的接口设计，避免 embedding 和 chat 混成一套。

你的回答：完全分离配置吧，采取你的建议
