注意：这里开发的模型既然好做工程化处理那不管是原先就的接口还是新接口都统一对外返回结构化结果，废掉原先只直接返回模型输出结果（str类型）的处理方式
本文档用于第一轮确认 Models 层 V1 正式化的设计问题。请直接在每个“你的回答：”后面填写答案。

说明：
- 这些问题不是考试题，目的是把 Models 层 V1 的职责边界、配置方式、provider 接入、模型路由、结构化输出、稳定性策略、日志指标和验收步骤定清楚。

- 旧 `Executor` 仍保留为 legacy 回退，但它的模型调用也需要同步迁移。Models 层 V1 的对外接口统一返回结构化结果，模型文本放在 `content` 等字段中，不再把裸字符串作为正式模型服务接口。
- 如果你不确定，可以写“按你的建议来”，后续我会按任务型 Agent 的常见工程做法给出保守方案。
- 有些问题后面写了“为什么要问”，方便你理解这个问题会影响哪部分设计。
- 如果本轮回答后仍有不明确的点，后续会继续生成 `Models设计问题回答(2).txt`、`Models设计问题回答(3).txt` 等。

当前 Models 层真实状态：


## 1. Models 层在整体 Agent 中的定位

### 问题 1：你是否同意 Models 层只负责“模型服务能力”，不重新承担 Analyzer / Planner / ReActExecutor 的职责？

通俗解释：
Analyzer 负责理解和路由；Planner 负责生成初始计划；ReActExecutor 负责执行循环、校验 ActionPacket、调用工具、生成 Observation 和 Checker 转移。Models 层不应该重新判断用户意图、不应该自己决定调用工具，也不应该生成 Observation。

建议：
Models V1 定位为统一模型服务层：

```text
请求封装
  -> provider 选择
  -> 模型调用
  -> 返回结构化 ModelCallResult
  -> 记录模型调用日志和指标
```

Models 层可以帮助解析 JSON 和做通用 repair，但不能替代 ReActExecutor 的 ActionPacket 业务校验。

为什么要问：
这决定 Models 层是基础服务层，还是会变成第二个执行器。

你的回答：是的


### 问题 2：Models V1 是否把 `generate()` 本身改为返回 `ModelCallResult` 等结构化结果？

通俗解释：
当前 Analyzer、Planner、legacy Executor 和 ReActExecutor 都直接调用 `generate()`，并期待拿到字符串。Models V1 正式化后，不应该再额外保留一个“字符串主接口”和一个“结构化新接口”，而应该直接修改 `generate()` 的返回类型，让所有调用方统一消费结构化结果。

建议：
正式对外接口统一为：

```python
generate(...) -> ModelCallResult
stream_generate(...) -> Generator[ModelStreamChunk, None, ModelStreamResult]
generate_json(...) -> StructuredModelResult
```

其中：

```python
ModelCallResult.content
ModelCallResult.success
ModelCallResult.error
ModelCallResult.code
ModelCallResult.provider
ModelCallResult.model
ModelCallResult.attempts
ModelCallResult.latency_ms
ModelCallResult.usage
```

`ModelCallResult.content` 保存模型正常生成的文本，其他字段保存调用状态、错误信息、provider/model、重试次数、耗时和 usage。`stream_generate()` 也不返回裸字符串 chunk，而是返回带内容、序号、结束状态和错误信息的 `ModelStreamChunk`。

Analyzer、Planner、ReActExecutor 以及 legacy Executor 都需要同步适配。需要字符串时只能显式读取 `result.content`，不能让 Models 层直接返回裸字符串。

为什么要问：
这决定 Models 层是否真正形成统一协议，也决定旧 Executor 和既有测试是否需要同步迁移。

你的回答：采取你的建议


### 问题 3：Models V1 的第一优先级是 provider 正式化，还是结构化输出正式化？

这里其实是在问：先解决“能不能稳定调用模型”，还是先解决“能不能正确消费模型返回结果”。
选项：

```text
A. 先 provider 正式化：配置、真实 API、timeout、retry、错误封装
B. 先结构化输出：JSON 解析、repair、schema、ActionPacket 支撑
C. 两者并行，但每个 Step 小步推进
```

建议：
选 C，但开发顺序先做“配置中心 + 结构化结果对象”，再做 provider 和 JSON 能力。原因是 provider 和结构化输出都需要统一调用结果对象支撑。

为什么要问：
这影响 Models 层开发步骤文档的 Step 1 / Step 2 排序。

你的回答：按你的建议来，先做共同底座，再逐步完成 provider 正式化和结构化输出正式化。


### 问题 4：Models V1 是否要把模型层视为“可观测服务”，而不是简单 SDK wrapper？

通俗解释：
真实模型调用会有超时、429、API key 缺失、网络失败、JSON 乱输出、成本、延迟、token 超限等问题。如果 Models 层只返回字符串，上层很难判断失败原因。

建议：
是。Models V1 应输出结构化调用记录，至少包含：

```text
success
content
error
code
provider
model
route
request_id
latency_ms
prompt_tokens
completion_tokens
total_tokens
cost
attempts
raw_response
metadata
```

为什么要问：
这决定后续日志、观测、重试和错误分类是否有统一基础。

你的回答：采取你的建议，既然模型单独做一层并且是基础服务层所以这些工程化细节需要做，因为这不仅仅只是简单的SDK模型接口调用了，为了后续可以稳定跑和观测需要这样做

## 2. 兼容接口与新协议

### 问题 5：正式模型接口失败时是否统一返回 `success=False` 的 `ModelCallResult`？

当前状态：
`ModelManager.generate()` 捕获异常并返回：

```text
Model call failed: ...
```

建议：
正式主接口不要把错误吞成普通文本，也不要把 provider 异常直接抛给业务层，而是经过重试后返回结构化失败：

```python
ModelCallResult(
    success=False,
    content="",
    error="...",
    code="model_call_failed",
    attempts=5
)
```

重试建议：

```text
最多重试 5 次
使用指数级退避
只有可重试错误才重试，例如 timeout / rate_limited / network_error / provider_server_error
重试后仍失败才返回 success=False
```

`generate()` 本身应直接返回 `ModelCallResult`，不再保留“返回错误字符串”的正式路径。模型文本放在 `content`，调用状态、错误码、重试次数、provider、耗时和 usage 放在其他字段中。所有调用方都必须先判断 `success`，再消费 `content`。

为什么要问：
如果模型失败被伪装成字符串，ReActExecutor 可能把错误文本当作模型回答继续消费。

你的回答：现有调用不是给什么消费什么吗，既然要改那就完整都进行修改，不要短期保留旧的处理方式了，直接统一修改成规定的格式让调用方知道模型generate()调用出错了（当然这个肯定需要经过规定的几轮重试后如果还是调用模型失败才这样处理，建议重试5次，指数级退避）
这里需要说下，既然模型层后续设计使用的是新的处理方式，那调用模型层然后进行消费的层也需要顺着新的设计处理做调整，这个不是死的，这个是一个系统，各部分是关联起来的，既然模型层要做新的调整那其他关联的就需要跟着做调整


### 问题 6：新接口是否需要区分“模型正常回答的文本”和“模型调用失败的错误”？

建议：
必须区分。`content` 只放模型真实生成内容；错误放到 `error/code`。

示例：

```python

    success=False,
    content="",
    error="OPENAI_API_KEY is not configured",
    code="missing_api_key"
)
```

为什么要问：
Analyzer / Planner / ReActExecutor 都需要知道失败是模型内容问题，还是模型服务问题。

你的回答：采取你的建议


### 问题 7：是否需要新增 `ModelMessage` 协议，支持 system/user/assistant 多消息，而不只是单 prompt 字符串？

通俗解释：

为什么要问：

你的回答：需要，采取你的建议，使用模板Prompt来做，区分角色

建议：
需要。建议先支持：

## 3. 模型配置中心

### 问题 9：Models 配置是否采用 `config/models/` 目录，而不是继续只放 `.env`？

建议：
采用配置文件 + 环境变量覆盖，并区分静态能力注册和运行时配置：

```text
config/models/
  models_config.json
  provider_specs.json
  provider_confs.json
  routes.json
  pricing.json
  structured_output.json
```

建议概念：

```text
ProviderSpec:
  静态注册表，描述 provider / protocol 的天生能力。
  例如 provider 类型、protocol、默认 base_url、默认模型、是否支持 streaming、json mode、embedding、vision、默认 timeout、请求/响应 adapter。

ProviderConf:
  运行时配置，描述用户实际启用的模型服务。
  例如显示名称、provider、protocol、base_url、api_key_env 或加密凭证引用、model_id、自定义 headers、状态。
```

`.env` 只放内置 provider 的密钥、默认 provider 和少量运行开关。用户通过“添加自定义模型”配置的 key，后续如果做 UI/Session 层，应进入本地加密凭证存储，而不是明文写入普通 JSON。

关键点：
ProviderSpec 和 ProviderConf 不应该只靠“模型名称”隐式串联。V1 应优先通过 `provider_conf_id` 显式选中运行时配置，再由 ProviderConf 中的 `provider/protocol` 找到对应 ProviderSpec。模型名称只用于指定本次调用的上游模型，不承担唯一识别 provider 配置的职责。

为什么要问：
provider endpoint、默认模型、超时、重试、路由、价格都放 env 会难以维护。

你的回答：可以，模型的配置专门进行管理


### 问题 10：`.env` 中是否继续保留 `MODEL_NAME`，还是改成 `DEFAULT_MODEL_PROVIDER`？

当前状态：

为什么要问：
“模型名”和“provider 名”不是一回事。`openai` 是 provider，`gpt-4o-mini` 才是模型名。

你的回答：旧配置不要了，直接换用新的配置方案吧，既然要使用新的方案那旧的方案就干脆抛弃，不然混在一起不好，要换就换干脆一些


### 问题 11：ProviderSpec 和 ProviderConf 至少需要哪些字段？

建议拆成两类字段。

ProviderSpec 至少包含：

```text
provider
protocol
display_name
default_base_url
default_model
supports_streaming
supports_json_mode
supports_tool_calling
supports_embedding
supports_vision
supports_custom_headers
default_timeout_seconds
default_max_retries
request_adapter
response_adapter
known_model_prefixes
tags
```

ProviderConf 至少包含：

```text
id
name
provider
protocol
enabled
base_url
api_key_env 或 credential_ref
default_model
custom_models
headers
timeout_seconds
max_retries
temperature
max_tokens
max_context_tokens
status
verified_at
metadata
```

为什么要问：
内置 OpenAI / Qianwen / Doubao 和用户自定义模型都需要走同一套抽象。ProviderSpec 解决“这类 provider 天生支持什么”，ProviderConf 解决“用户当前配置了哪个 endpoint/key/model”。

补充建议：
ProviderConf 应该能被 `provider_conf_id` 唯一引用。路由层、verify、health check、日志和未来 UI 都基于这个 id 找到具体 endpoint、凭证和默认模型，而不是根据模型名称猜测配置。

你的回答：采取你的建议，如果有实际需求除了你建议里面的字段可以再增添字段


### 问题 12：密钥如何存储，内置 provider 和用户自定义 provider 是否分开处理？

建议：
密钥不要明文写入普通配置文件。建议分两类处理：

```text
内置 provider:
  从环境变量读取，例如 OPENAI_API_KEY / DASHSCOPE_API_KEY。
  ProviderConf 里只写 api_key_env。

用户自定义 provider:
  后续如果有管理界面，key 应进入本地加密凭证存储。
  ProviderConf 里只写 credential_ref。
```

示例：

```json
{
  "id": "conf_openai_default",
  "provider": "openai",
  "api_key_env": "OPENAI_API_KEY",
  "credential_ref": null
}
```

用户自定义配置示例：

```json
{
  "id": "conf_my_deepseek",
  "name": "我的 DeepSeek",
  "provider": "custom",
  "protocol": "openai-compatible",
  "base_url": "https://api.deepseek.com/v1",
  "credential_ref": "cred_my_deepseek",
  "default_model": "deepseek-chat"
}
```

为什么要问：
避免把 API key 写入项目配置文件或日志，同时给后续类似 Cursor 的“添加自定义模型”能力预留安全存储方式。

你的回答：从环境变量读取


### 问题 13：如果配置文件不存在或字段缺失，Models 层应该如何降级？

建议：
不静默降级到 `mock`。如果调用方请求真实模型，但配置文件不存在、字段缺失、provider 未启用、模型名缺失或 API key 缺失，Models 层应返回结构化失败，而不是自动切换成 mock：

```python
ModelCallResult(
    success=False,
    content="",
    error="model configuration is missing",
    code="missing_model_config"
)
```

MockModel 只在显式配置为 mock 或测试 fixture 明确注入 mock 时使用。

为什么要问：
这决定“配置错误”会不会被隐藏。真实用户使用时，缺模型配置应该让 Runtime/API/UI 层能明确提示用户去配置模型，而不是让 Agent 看似正常但实际返回 mock 内容。

你的回答：Models 层不应在真实模型未配置时静默降级到 mock。
如果调用方请求真实模型，但配置不存在、provider 未启用、模型名缺失或 API key 缺失，应返回结构化失败：

ModelCallResult(
    success=False,
    content="",
    error="model configuration is missing",
    code="missing_model_config"
)
上层根据错误码生成用户可见提示，例如“当前模型未配置，请先配置模型 API key 或切换到 mock 模式”。


### 问题 14：真实 provider 未配置 API key 时，是否应该在初始化时报错？

当前状态：
`OpenAIModel/QianwenModel/DoubaoModel.__init__()` 缺 key 直接抛异常。

provider 初始化可以成功，但 `health_check()` 返回 false；真实调用时返回结构化 `missing_api_key`。这样 `ModelManager` 可以启动并给出清晰状态。

为什么要问：
如果初始化时报错，`MODEL_NAME=openai` 但没 key 时整个 Agent 可能无法启动。

你的回答：采取你的建议，agent的正常启动能被是否配置过模型束缚，agent启动和一些初始化可以正常走，只是在和agent交谈时发现模型调用不了再提示没有配置API key

## 4. Provider 优先级与真实集成边界
Provider 是什么东西？
回答：Provider
  -> 管 API 地址、鉴权方式、请求格式、响应解析方式
  -> 下面可以挂多个 model
  不同的模型在鉴权，请求，响应的数据结构方面都不一样，所以需要一个Provider来调度管理
### 问题 15：真实 provider 的优先正式化顺序是什么？

选项：

```text
A. OpenAI 优先
B. Qianwen / DashScope 优先
C. Doubao 优先
D. 三个 provider 都先统一配置和接口，真实联调按 key 可用性后置
```

建议：
选 D。先做统一 provider 接口和 mock 测试；真实 API 集成测试检测到对应 API key 时才运行。

为什么要问：
这影响第一批 provider 代码是否需要真实网络验收。

你的回答：采取你的建议


### 问题 16：OpenAI provider 是否使用官方 `openai` SDK，还是继续兼容当前写法？

建议：
使用 `openai` SDK 的新客户端方式，但封装在 provider 内，不让上层感知 SDK 细节。当前 `openai.api_key = ...` 的全局状态写法应逐步替换。

为什么要问：
全局 SDK 状态不利于多 provider、多 base_url、多模型路由和测试隔离。

你的回答：采取你的建议，使用 `openai` SDK 的新客户端方式


### 问题 17：Qianwen provider 使用 DashScope 原生接口，还是走 OpenAI-compatible endpoint？

背景：
Qianwen 可以有不同接入方式。当前代码使用 DashScope text-generation HTTP 接口。

建议：
V1 优先统一使用 OpenAI-compatible endpoint。Qianwen 不再优先走 DashScope 原生 text-generation 接口，而是通过 OpenAI-compatible 协议接入，统一 messages、streaming、JSON 输出和错误处理。

原生 DashScope 接口可以作为后续 provider variant 预留，但不作为 V1 主路径。

为什么要问：
这影响请求/响应解析和流式输出实现。

### 问题 19.1：添加自定义模型后是否必须支持验证 Verify 流程？

### 问题 19.2：ProviderConf 是否在 V1 就预留多凭证结构？

通俗解释：
同一个 provider 或同一个 base_url 可能有多个 API key，比如不同账号、不同额度、不同用途。你的自定义模型想法里提到每个 key 可以有一个 `slug`，请求时可指定使用哪个 key，并支持后续成本隔离和故障切换。

建议：
V1 数据结构应正式预留多凭证，但实现可以先只默认使用 `default`：

```text
credentials:
  - slug: default
    api_key_env: OPENAI_API_KEY
    credential_ref: null
    enabled: true
    status: active

route candidate:
  provider_conf_id
  credential_slug
  model
```

内置 provider 可以先走 `api_key_env`；用户自定义 provider 后续走本地加密 `credential_ref`。即使 V1 不做完整多账号 UI，路由、日志、熔断和错误码也要按 `credential_slug` 预留字段。

为什么要问：
如果现在只把 key 做成 ProviderConf 的单个字段，后续加多 key / 多租户 / 配额隔离时会反复改路由和日志结构。

你的回答：采取你的建议，V1就需要做多凭证结构


### 问题 19.3：非 OpenAI-compatible 协议在 V1 做到什么程度？

通俗解释：
你的想法里提到 Anthropic、Gemini、非标准 API 都可以通过适配器接入。但它们的请求/响应格式和 OpenAI Chat Completions 不完全一样，如果 V1 全部做完，会显著扩大范围。

建议：
V1 明确分层：

```text

  openai-compatible

配置和枚举预留:
  anthropic-compatible
  gemini-compatible
  custom-mapping

暂不完整实现:

```

也就是说，Claude 如果通过 OpenAI-compatible 网关或 OpenRouter 接入，V1 可以支持；如果直接走 Anthropic Messages API，V1 先预留 provider variant，后续再做。

为什么要问：
这能避免 Models V1 被“所有模型协议全兼容”拖住，同时不破坏未来扩展路线。

你的回答：V1 正式实现 OpenAI-compatible。
anthropic-compatible 和 gemini-compatible 先进入协议枚举和配置预留，后续再实现原生 adapter。

OpenAI-compatible      = 按 OpenAI 风格发请求
anthropic-compatible   = 按 Claude / Anthropic 风格发请求
gemini-compatible      = 按 Gemini / Google 风格发请求


### 问题 19.4：自定义 Request Body / Response JSON Path 映射是否放到 V2？

通俗解释：
有些模型服务不是 OpenAI-compatible，可能要求把 `messages` 改成 `inputs`，把返回内容从某个特殊 JSON 路径取出来。你的想法里称为高级模式。

建议：
V1 先不实现完整模板引擎，只预留配置字段：

```text

response_mapping
headers
protocol = custom-mapping
```

为什么要问：
请求映射能力很强，但也带来安全、测试和错误诊断复杂度。先预留字段可以保证架构不堵死，但不会影响 V1 小步推进。

你的回答：采取你的建议，就是说这个情况只在调用一些私有的模型时协议混乱的时候才会遇到，所以V1暂时不考虑这个，因为一般都使用那种公有的模型那种使用正常协议和字段的模型

### 问题 21：路由配置是否按调用类型配置？

建议：
使用 `routes.json`：

```json

  "react_action_decision": [

      "provider_conf_id": "conf_openai_default",
```

### 问题 22：如果主路由模型失败，是否自动切到 fallback 模型？

建议：
V1 支持可配置 fallback，但要保守：

```text
missing_api_key -> 可 fallback
timeout -> 可 fallback
rate_limited -> 可 fallback
server_error -> 可 fallback
schema_invalid -> 先 repair，再视情况 fallback
blocked_by_policy -> 不 fallback
invalid_prompt -> 不 fallback
```

如果启用多候选路由，建议区分冷却粒度：

```text
401 / 403
  -> 冷却当前 credential_slug

404 / 429 / 5xx / timeout / network_error
  -> 冷却当前 provider_conf_id + model

schema_invalid
  -> 先 repair，再视情况切换候选
```

为什么要问：
fallback 可以提升稳定性，但不能掩盖系统错误或安全阻断。

你的回答：同意，fallback 就是模型调用失败后的备用模型/备用路由切换策略。V1 支持可配置 fallback，但必须按错误类型保守处理，不能用 fallback 掩盖安全阻断或请求本身错误。
适合 fallback：
missing_api_key：当前模型没配置 key，换一个已配置的
timeout：当前模型超时，换一个
rate_limited：当前模型限流，换一个
server_error：当前模型服务端故障，换一个
schema_invalid：模型返回 JSON 不合格，先 repair，修不好再考虑换
等等...

## 6. 结构化输出与 JSON repair

### 问题 25：Models 层是否需要提供通用 `generate_json()`？

建议：
需要。Analyzer LLM fallback、Planner LLM planner、ReActExecutor ActionPacket 都需要 JSON 输出。通用接口可以做：

```text
调用模型
提取 JSON object / array
基础 JSON 解析
按 schema 做轻量校验
失败时构造通用 repair prompt
返回 StructuredModelResult
```

但 ActionPacket 的业务校验仍留在 ReActExecutor。

为什么要问：
这决定 JSON 解析逻辑是继续散落在 Analyzer / Planner / ReActExecutor，还是逐步抽到 Models 层复用。

你的回答：采取你的建议，第一阶段：Models 层做通用 JSON 处理，第二阶段：ReActExecutor 做 ActionPacket 业务校验和执行翻译
Models 层：把模型输出解析成 JSON
ReActExecutor：判断这个 JSON 是不是可执行的 ActionPacket
ReActExecutor 不是直接翻译成 shell 命令，而是把 JSON 校验成 ActionPacket，再通过 Tool 层执行。



### 问题 26：通用 JSON 解析应该宽松还是严格？

当前现状：
- Analyzer / Planner 支持从 fenced JSON 或带说明文字中提取 JSON。
- ReActExecutor 主路径对 ActionPacket 更严格，不接受“自然语言夹 JSON”作为可执行动作。

建议：
Models 层提供两种模式：

```text
strict_json: 只接受纯 JSON object/array 或完整 fenced JSON
lenient_json: 可从自然语言中提取第一个 JSON object/array
```

ReActExecutor ActionPacket 默认用 strict；Analyzer / Planner 可按场景使用 lenient。

为什么要问：
结构化动作越靠近执行器，越不能靠猜。

你的回答：采取你的建议，Prompt 规定模型应该返回某种 JSON
  -> 模型返回文本
  -> Models 层提取 / 解析 / 修复 / 基础校验 JSON
  -> 返回 StructuredModelResult
  -> 上层再做业务语义校验


### 问题 27：JSON repair 最大次数应由 Models 层统一配置，还是各调用方自己配置？

建议：
两级配置：

```text
Models 默认 max_json_repair_attempts
调用方可覆盖，例如 ReActExecutor 使用 max_action_packet_repair_attempts
```

为什么要问：
Analyzer、Planner、ReActExecutor 对 repair 成本和风险的容忍度不同。

你的回答：采取你的建议


### 问题 28：结构化输出失败时，Models 层返回什么？

建议：
返回：

```python
StructuredModelResult(
    success=False,
    parsed=None,
    raw_text="...",
    errors=["no JSON object found"],
    repair_attempts=2,
    model_result=ModelCallResult(...)
)
```

不要把失败伪装成 `{}` 或默认成功结构。

为什么要问：
上层需要明确知道是模型没给 JSON，而不是任务本身失败。

你的回答：采取你的建议（再重试指定次数后如果还是没有得到正确的json就需要这样做）


### 问题 29：是否需要支持 JSON Schema 校验库？

建议：
V1 可先实现轻量 schema 校验，不强依赖 `jsonschema` 包；如果后续 schema 复杂，再加入依赖。

为什么要问：
新增依赖会影响 requirements 和测试环境，轻量校验足够支撑 V1 早期。

你的回答：采取的建议


### 问题 30：ActionPacket repair 逻辑是否迁移到 Models 层？

建议：
不迁移业务逻辑。Models 层只提供通用 repair 能力；ReActExecutor 继续负责：

```text
字段级业务校验
```

为什么要问：
ActionPacket 是执行器协议，不是通用模型协议。迁移太多会让 Models 层耦合执行器。

你的回答：采取你的建议

## 7. ReActExecutor 模型交互专项

### 问题 31：ReActExecutor ActionPacket 决策是否走专门 route？


### 问题 33：模型返回的 `thought_summary` 是否可以展示给用户？

建议：

为什么要问：

为什么要问：
ReActExecutor 不直接执行 shell，命令必须走 Tool 层。Models 层更不能执行 shell。

你的回答：采取你的建议，还是前面提到的模型层只做属于他的工作

## 8. 流式输出与用户事件

### 问题 36：Models V1 是否需要保留 `stream_generate()`？

建议：
保留，但第一阶段重点不是 UI 流式，而是结构化调用稳定性。`stream_generate()` 先服务普通文字生成；ActionPacket 决策默认仍用非流式完整 JSON，避免半截 JSON 解析问题。

为什么要问：
ReActExecutor 已经有 `execute_stream()` 用户事件流；这和 provider token streaming 是两层不同的流。

你的回答：采取你的建议


### 问题 37：provider token streaming 是否要直接暴露给用户事件流？

建议：
不要直接暴露。Models 层输出 token chunk；ReActExecutor / Runtime 决定哪些 chunk 变成 `message_delta` 或内部事件。

为什么要问：
用户事件和开发日志已经分离，Models 层不能越过执行层直接面向用户。

你的回答：采取你的建议


### 问题 38：结构化输出是否允许流式？

建议：
V1 不做结构化 JSON 流式解析。ActionPacket、Planner JSON、Analyzer JSON 都等完整响应后解析。

为什么要问：
流式 JSON 解析复杂且容易产生半截结构，V1 不值得引入。

你的回答：模型输出的结构化json还是不要做流式了，免得解析出错，直接使用非流式得到完整的json再做解析处理

## 10. 超时、重试、熔断、限流

### 问题 42：每次模型调用是否必须有 timeout？

建议：
必须有 provider 默认 timeout，也允许调用方覆盖。

示例：

```text
default_timeout_seconds = 30
react_action_decision timeout = 20
summary timeout = 60
embedding timeout = 30
```

为什么要问：
没有 timeout，Agent 执行会卡死在外部模型服务上。

你的回答：采取你的建议，不过不管是哪种timeout至少大于40s，增加超时判定时间


### 问题 43：retry 由 Models 层做，还是由 ReActExecutor 做？

建议：
模型服务调用层面的 retry 由 Models 层做，默认最多 5 次并使用指数级退避；ActionPacket schema repair、工具动作 retry 仍由 ReActExecutor 做。

区分：

```text
Models retry: timeout / 429 / 5xx / network_error / provider_server_error
ReActExecutor repair: 模型返回 JSON 不合法
ReActExecutor retry_step: 工具或动作执行失败后的业务重试
```

Models retry 耗尽后返回：

```python
ModelCallResult(
    success=False,
    code="model_call_failed",
    attempts=5
)
```

为什么要问：
不同 retry 语义不同，混在一起会让日志和成本无法解释。

你的回答：采取你的建议，模型层面的超时或者其他非原则性失败由模型层重新向模型发送请求，指定次数后依然失败直接返回失败结构化数据给调用方，然后调用方做处理（记录日志，提示用户等等）如果是工具或者命令执行失败那这个就由执行层去重试了


### 问题 44：是否需要熔断机制？

通俗解释：
如果一个 provider / credential / model 连续失败，短时间内不再反复调用同一个失败候选，直接走下一个路由候选或返回结构化失败。

建议：
V1 做轻量内存熔断，并区分冷却粒度：

```text
401 / 403:
  当前 credential_slug 进入冷却

404:
  当前 provider_conf_id + model 进入冷却

429:
  当前 provider_conf_id + model 或 credential_slug 进入冷却，按 provider 返回信息判断

5xx / timeout / network_error:
  当前 provider_conf_id + model 进入短冷却

连续失败 N 次:
  route candidate 标记 circuit_open

health_check / verify 成功:
  恢复候选
```

如果你想压缩 V1 范围，也可以先只预留接口，Step 3 再做。

为什么要问：
真实 provider 或用户自定义模型故障时，Agent 不应每一步都卡在同一个失败候选上；但也不应该因为一个 key 失效就禁用同 provider 下所有模型。

你的回答：采取你的建议，但是你给的冷却粒度还需要细化一下，完善一下，基于这个雏形设计一个全面的冷却粒度方案，比如可能还会有其他的错误码、捕获关键错误信息(有些模型可能有自己的错误码或者错误消息，但是错误消息基本大差不差所以需要捕获一些错误消息来进行判断)


### 问题 45：是否需要本地限流？

建议：
V1 可先做配置占位，不实现复杂限流。先记录 `rate_limited` 并支持 retry/fallback。

为什么要问：
限流和并发控制更适合 Runtime/API 层统一做，但 Models 层要能识别 provider 的 429。

你的回答：采取你的建议

## 11. Token、成本、上下文长度

### 问题 46：Models V1 是否需要 token 统计？

建议：


为什么要问：
成本统计、上下文压缩和运行观测都依赖 token 信息。

你的回答：采取你的建议


### 问题 47：是否需要成本估算？

建议：

```text

```

为什么要问：

你的回答：成本估算就不需要了吧，毕竟这个也只是一个agent，成本监控我在模型接口提供方我可以查看成本消耗情况的


### 问题 48：上下文超长时由谁负责压缩？

建议：
各层分工：

```text
Analyzer / Planner / ReActExecutor: 构造合适上下文和摘要
Models 层: 根据 provider/model max_context_tokens 做最后长度检查，超限时返回 context_length_exceeded 或触发可配置截断
Memory / RAG: 后续负责历史压缩和检索
```

Models 层不要擅自删除关键结构字段，除非调用方明确允许。

为什么要问：
模型层自动截断 prompt 可能破坏 ActionPacket 或计划上下文。

你的回答：这个压缩可以交由模型来做，确保保留关键信息，历史信息也需要交给模型进行压缩，不然一个Session越到后面的对话如果需要依赖前面对话的结果的话这是就需要对前文历史进行压缩，所以这个上下文压缩后续问答我觉得有必要进行详细的设计，毕竟这个东西涉及到了我的agent是否有良好的记忆和联系上下文的功能，这个需要和记忆层联动，记忆层联合模型层共同做一个Session的上下文对话的压缩记忆，还有就是在执行器和Planner内部有些地方需要多次调用模型并且严重依赖前面模型执行结果、工具执行结果、执行器和各个任务执行状况的地方也需要设计压缩，比如设计一个阈值的那个文字超过后那就需要进行压缩了，所以这个上下文压缩功能有许多地方都可能会涉及

为什么要问：
结构化输出稳定性和自然语言质量需要不同采样参数。

你的回答：采取你的建议，这个不就是前面提到过的调用同一个模型（用户指定的），然后不同情况使用不同的调用策略吗
