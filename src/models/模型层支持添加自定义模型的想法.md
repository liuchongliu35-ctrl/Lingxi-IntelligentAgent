## 一、核心理念定位

**“模型即插即用（Plug-and-Play Model）”** ——将底层大模型API抽象为可动态注册的“数据源（Provider）”，用户通过输入“端点（URL）+ 凭证（Key）+ 模型标识（Model ID）”即可热插拔任意兼容或非兼容的模型服务。

这一设计理念的出发点在于：**换模型不该动代码**。Cursor等产品的实践表明，用户需要的不是“连上就行”，而是“让Agent像原生支持一样稳定调度第三方模型”。因此，系统应从协议层、会话层、语义层三个维度同步对齐，而非仅提供UI表单填写。


## 二、架构分层设计

参考行业主流实践（如Lens的多协议网关架构、LiteLLM的统一接口模式），系统分为以下四层：

### 1. 配置层（Configuration Layer）

**设计原则：两套配置，各管各的事**

- **ProviderSpec（静态注册表）**：代码中维护模型提供商的“天生属性”——如模型名称关键字、是否支持深度搜索、是否支持联网、默认超时设置等。这些东西跟运维参数无关，是模型本身的特性，更新频率很低。
- **ProviderConf（运行时配置）**：用户在界面中配置的动态信息——API密钥、访问地址、要用的具体模型名。这些经常变化，单独抽出来动态加载。

两者通过**模型名称**字段串联：创建实例时，先用用户指定的模型名去静态注册表查出对应的ProviderSpec，再与Conf一并传给Provider类构造函数。

**存储规范**：敏感信息（API Key）使用AES-256加密存储，绝不明文落盘。

### 2. 适配层（Adapter Layer / Gateway）

**核心模式：策略模式（Strategy Pattern）+ 工厂模式（Factory Pattern）**

定义一个`LLM Provider`抽象基类，规定统一接口契约。核心方法有两个：`chat`和`chat_stream`。每个子类实现特定厂商的API调用逻辑：

1. 将通用参数拼装成目标API需要的格式
2. 发起HTTP请求
3. 将厂商特有的返回结构解析成统一的`LMResponse`对象

**`LMResponse`是关键**——它定义了一套标准字段集，不管底层用的是哪家模型，上层拿到的都是同一个数据结构。后续的重试判断、内容脱敏、回调处理全部基于这套标准字段来做。

**协议兼容策略**：
- **默认采用OpenAI Chat Completion API规范**作为基线（这是当前最广泛兼容的标准）
- **高级模式**：允许用户自定义Request Body的JSON Path映射（如将`messages`重命名为`inputs`，将`temperature`重命名为`temp`），实现非标准API的接入

### 3. 路由层（Router Layer）

**设计理念参考：Lens的模型组路由机制**

- 按“运行时渠道 + 凭证 + 上游模型”组成路由候选
- 支持**轮询（Round Robin）** ：在候选之间平滑分发请求
- 支持**故障切换（Failover）** ：按顺序尝试，失败后自动切换到下一个凭证/渠道
- **冷却粒度设计**：
  - 401/403错误 → 冷却当前凭证
  - 404/429/5xx/超时/网络错误 → 冷却该模型
  - 同渠道其他模型继续可用

### 4. 可观测层（Observability Layer）

记录每次请求的完整生命周期：协议类型、模型名称、延迟、Token消耗、成本、User-Agent、每次上游尝试的链路和错误摘要。这是企业级生产环境的基本要求。


## 三、用户体验流程设计

### 模式一：快速预设（Preset Provider）

下拉菜单提供“DeepSeek”、“OpenRouter”、“Groq”、“Anthropic”等知名平台，选中后**自动填入标准的Base URL和推荐模型名**，用户只需填入API Key。

这一设计参考了OpenRouter的理念：**认证应让用户快速进入可用状态，模型管理应放在专门的流程中**。首次体验不应让用户面对数百个模型的选择。

### 模式二：完全自定义（Custom Provider）

提供“添加自定义模型”按钮，必填项包括：
- **显示名称**：用户自定义的模型别名
- **API地址（Base URL）** ：模型服务的端点
- **API Key**：访问凭证
- **模型名称（Model ID）** ：具体要调用的模型标识

可选项包括：
- 最大上下文长度
- 是否支持视觉（Vision）
- 请求超时时间
- 自定义请求头（Headers）

### 校验机制（Connectivity Test / Verify）

**这是用户体验的关键环节**。参考Cursor和Anchor的实践：

点击“验证（Verify）”按钮后，系统发送一条极简的Ping请求（如`{"messages":[{"role":"user","content":"hi"}]}`）到该URL。这一环节远不止是HTTP Header里塞个Bearer Token——它要校验的是：
- 会话级可信通道是否建立
- Token是否具备对应模型的操作权限
- 响应体结构是否符合预设的JSON Schema

验证通过后才允许保存配置，避免用户存储无效配置。

### 模型管理入口分离

参考OpenRouter的设计：
- **主界面（/model）** ：仅展示用户已启用的模型，作为快速切换器
- **管理界面（/manage-models）** ：独立的模型管理入口，支持浏览发现、按ID/名称/提供商前缀搜索、按标签（如free/vision）筛选、批量启用/禁用

这一分离设计确保主界面简洁，同时为未来接入ModelScope、ModelStudio等更多模型来源保留扩展能力。


## 四、数据模型定义

```json
{
  "id": "uuid",
  "name": "我的私有DeepSeek",
  "provider_type": "openai-compatible",  // 或 "anthropic-compatible" / "custom"
  "base_url": "https://api.deepseek.com/v1",
  "api_key": "sk-xxxxx",  // 存储时使用 AES-256 加密
  "default_model": "deepseek-chat",
  "custom_models": ["deepseek-coder"],
  "config": {
    "max_tokens": 4096,
    "timeout": 30,
    "headers": { "X-Custom-Header": "value" }
  },
  "status": "active",  // active | inactive | error
  "verified_at": "2026-08-06T10:00:00Z"
}
```

### 多凭证支持

参考Anchor的设计和ALLM的五级密钥解析链，每个Provider可配置**多个API Key**（例如为同一提供商准备多个账号的Key），每个Key有一个短名称（slug）用于引用。请求时可指定使用哪个Key，实现：
- 成本分摊与隔离
- 配额管理与故障切换
- 多租户场景下的密钥隔离


## 五、安全与合规设计

### 1. BYOK（Bring Your Own Key）模式

用户自带密钥访问自己的模型提供商。核心原则：
- **密钥只存本地**：绝不经过我们的后端服务器
- **用户控制身份层、模型提供商和计费**
- **请求直达提供商**：LLM请求直接发送到用户指定的提供商，不经过我们的推理层

### 2. 代理转发（Proxy/Relay）

为了解决前端直接调用AI API的CORS限制问题，设计一个**纯转发（Pure Proxy）** 的后端接口：
- 不记录请求体和响应体（仅做透传）
- 不存储用户密钥
- 仅用于附带用户自定义的URL和Key发起请求
- 支持自托管部署

### 3. 故障隔离（Fault Isolation）

自定义模型的调用运行在独立的异步线程/协程中，并设置严格的超时（Timeout）和重试（Retry）机制。单个自定义模型的超时或报错，**绝不阻塞Agent主界面或其他内置模型的调用**。


## 六、兼容性策略总结

| 场景 | 策略 |
|------|------|
| OpenAI兼容API | 默认支持，用户填入Base URL + Key即可 |
| Anthropic Messages API | 通过适配器模式转换协议 |
| Gemini API | 通过适配器模式转换协议 |
| 非标准API | 提供“模板引擎”，允许用户自定义请求体字段映射 |
| 自托管模型（Ollama/vLLM等） | 通过OpenAI兼容端点接入 |
| 云厂商私有化部署 | 通过自定义Base URL + 自定义Header支持 |


## 七、设计总结（可直接引用）

> **“本系统关于‘自定义模型添加’的设计，采用‘配置驱动（Configuration-Driven）’与‘适配器模式（Adapter Pattern）’相结合的策略。我们将模型交互抽象为‘端点（Endpoint）’、‘凭证（Credential）’和‘协议（Protocol）’三要素。用户界面提供从‘预设知名厂商’到‘完全手动输入’的灵活梯度，后台通过‘ProviderSpec + ProviderConf’双配置机制实现静态特性与运行时配置的分离，通过策略模式动态实例化HTTP客户端实现协议适配与转换。**
>
> **核心设计原则为：前端配置隔离、本地加密存储、协议自适应兼容、请求安全透传、故障自动隔离——在极高的扩展性下，维持系统的稳定性与用户数据的安全性。**
>
> **参考行业实践，模型管理入口与日常使用入口分离，认证流程让用户快速进入可用状态，而模型筛选与管理放在专门的流程中。路由层支持轮询与故障切换，可观测层记录完整请求链路，共同构成生产级的多模型接入体系。”**
