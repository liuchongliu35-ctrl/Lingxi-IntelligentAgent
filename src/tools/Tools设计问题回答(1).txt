# Tools 设计问题回答（1）

本文档用于第一轮确认 Tools 层 V1 正式化的设计问题。请直接在每个“你的回答：”后面填写答案。

说明：
- 这些问题不是考试题，目的是把 Tools 层 V1 的职责边界、ToolResult 协议、ToolRegistry / ToolManager 关系、基础工具范围、命令与文件安全、联网搜索方案、权限确认、日志观测、错误分类和验收步骤定清楚。
- Tools 层必须服务当前已经完成的 Analyzer V1、Planner V1、ReActExecutor V1 第二阶段和 Models V1，不重新设计这些层的主链路。
- 当前外部编排链路已经是：

```text
用户输入
  -> ReactAgent
  -> Analyzer
  -> Planner
  -> ReActExecutor
  -> 输出反馈处理器
  -> 用户反馈
```

`输出反馈处理器` 是主链路收尾边界，负责把 ReActExecutor / ReactAgent 产出的 `ExecutionEvent` 和 `ExecutionResult` 转换成用户可见反馈。它不重新做 Analyzer、Planner 或 ReActExecutor 的决策，也不直接执行工具。

`ExecutionResult` 和 `ExecutionEvent` 不是独立业务层，而是 ReActExecutor / ReactAgent 对上层返回的结构化输出协议：

```text
ExecutionResult:
  一次执行结束后的最终结构化结果，例如 status、success、output、summary、observations、events、pending_confirmation、error_code。

ExecutionEvent:
  执行过程中的事件流对象，例如 step_started、tool_started、tool_finished、observation_created、final_answer。
```

执行器内部通过模型或执行器规则生成的用户可见步骤说明，例如计划摘要、动作摘要、工具进度、阶段性说明和确认请求，应作为摘要化 `ExecutionEvent` 交给输出反馈处理器。原始 prompt、内部推理、工具 raw output、异常堆栈和开发日志不直接进入用户反馈。

其中 `Observation` 和 `Checker` 也不是独立于执行器之外的新主链路层，而是 ReActExecutor 内部执行循环中的环节。ReActExecutor 在执行 `ActionPacket` 时，可能会按动作类型调用 Tool 层、Models 层、User 控制或 Control 动作：

```text
ReActExecutor 内部循环：
  ActionPacket
    -> 调用 Tool / Model / User / Control
    -> 根据真实调用结果生成 Observation
    -> Checker 判断继续、重试、完成或终止
    -> 记录事件，并最终汇总为 ExecutionResult
```

这里的 `Model` 调用只表示 ReActExecutor 内部可能使用 Models 层，并不表示 Models 层是 ReActExecutor 的内部子模块。Models 层是项目级基础模型服务层，Analyzer、Planner、ReActExecutor 以及后续 Memory / RAG 等模块都可以调用它。旧顺序 Executor 只是早期原型/历史诊断参考，不再作为正式适配目标。

当前项目分层总览：

```text
已完成或作为当前核心主链路：
  ReactAgent 编排层
  Analyzer 层
  Planner 层
  ReActExecutor 层
  输出反馈处理器

基础服务层：
  Models 层
  Tools 层

后续支撑与增强层：
  Runtime / API / Session 层
  Memory 层增强
  RAG / 知识库层增强
  安全与权限层统一（安全策略层）
  配置、日志、观测与端到端验收工程
```

各层关系简述：

```text
ReactAgent:
  接收用户输入，串联 Analyzer / Planner / ReActExecutor，并向上层暴露 run / run_with_result / run_stream。

Analyzer:
  负责理解输入、识别意图、参数、风险和执行策略。

Planner:
  负责生成 TaskPlan / TaskUnit / PlanStep。

ReActExecutor:
  负责执行 Planner-guided ReAct 循环，调用 Tool / Model / User / Control，生成 Observation、事件和最终结果。

输出反馈处理器:
  负责把 ExecutionEvent / ExecutionResult 整理成用户能看到的过程反馈和最终回答。

Models:
  项目级基础模型服务层，可被 Analyzer、Planner、ReActExecutor 和后续 Memory / RAG 调用；旧顺序 Executor 不再作为正式适配目标。

Tools:
  项目级工具能力服务层，提供真实外部能力并返回 ToolResult；当前主要由 ReActExecutor 通过 ActionPacket 调用。
```

模型作为大脑的关键原则：

```text
本项目目标是模型作为大脑的灵活任务型 Agent，不是规则硬编码结果的固定流程助手。
```

Tools V1 设计时必须注意：

```text
工具层负责真实执行、结构化返回、权限边界、错误分类、日志审计。
工具层不负责替代模型理解用户意图，不负责生成复杂计划，不负责决定下一步动作。
需要理解、判断、生成、决策、总结、修复的地方，应保留或调用 Models 层。
```

典型边界：

```text
Analyzer:
  LLM fallback 通过 Models 层做意图、参数、风险、复杂度和执行策略兜底。

Planner:
  LLM planner fallback 通过 Models 层生成结构化计划。

ReActExecutor:
  Thought / ActionPacket 决策、ActionPacket repair、call_model、fallback_to_model、复杂总结和 final answer 都应走 Models 层。

Tools:
  普通工具只做真实执行。
  web_search 的 model_builtin provider、后续模型翻译/摘要/改写工具可以通过 Models 层调用。
```

规则适合用于 schema 校验、权限与安全边界、错误码分类、timeout/retry/fallback 策略和测试 fake/mock，不应硬编码复杂计划、ActionPacket 决策、最终回答或模型总结来冒充模型能力。

- ReActExecutor 已经要求模型通过 `ActionPacket` 等结构化协议指挥执行器；工具调用必须由 ReActExecutor 校验后执行。
- Observation 必须由执行器根据真实 Tool / Model / User / Control 结果生成，模型不能伪造 Observation。
- ReActExecutor 不直接执行 shell；命令必须走 Tool 层。
- 用户可见 events 和开发 logs 必须分离。
- Models V1 已经正式化，Tools V1 应消费或配合现有 Models / ReActExecutor 结构化协议，不重做模型层。
- Tool 层必须返回真实、结构化、可审计的 ToolResult，不能让模型直接伪造工具执行结果。
- 如果你不确定，可以写“按你的建议来”，后续我会按任务型 Agent 的常见工程做法给出保守方案。
- 有些问题后面写了“为什么要问”，方便你理解这个问题会影响哪部分设计。
- 如果本轮回答后仍有不明确的点，后续会继续生成 `Tools设计问题回答(2).txt`、`Tools设计问题回答(3).txt` 等。

## 1. Tools 层在整体 Agent 中的定位

### 问题 1：你是否同意 Tools 层只负责“真实外部能力执行”，不承担 Analyzer / Planner / ReActExecutor 的职责？

通俗解释：
Analyzer 负责理解用户意图，Planner 负责制定计划，ReActExecutor 负责执行循环、ActionPacket 校验、确认、调用工具和生成 Observation。Tools 层不应该自己判断任务路线，也不应该自己生成 Observation，更不应该让模型绕过执行器直接执行工具。

建议：
Tools V1 定位为统一工具服务层：

```text
接收已校验的工具调用请求
  -> 根据 ToolSpec / ToolPolicy 做参数、安全、权限、超时校验
  -> 执行真实工具
  -> 返回结构化 ToolResult
  -> 写入开发日志 logs/tools.log
```

工具可以返回执行结果和审计信息，但不决定下一步该做什么。下一步动作仍由 ReActExecutor 根据 Observation / Checker / ActionPacket 决定。

为什么要问：
这决定 Tools 层是基础执行服务，还是会膨胀成第二个执行器。

你的回答：采取你的建议


### 问题 2：Tools 层是否允许模型直接调用工具？

通俗解释：
模型可以生成 `ActionPacket`，其中包含 `tool_name` 和 `args`，但真正调用工具的人应该是 ReActExecutor，而不是模型 provider 或 Models 层。

建议：
不允许模型直接调用工具。正式链路应是：

```text
Model 生成 ActionPacket
  -> ReActExecutor 解析和校验
  -> ToolRegistry 校验工具是否存在、参数是否合规、风险是否允许
  -> 需要确认时进入 confirmation 流程
  -> ToolManager / ToolRuntime 执行真实工具
  -> ToolResult
  -> ReActExecutor 生成 Observation
```

为什么要问：
如果模型能直接调用工具，Observation、权限确认、日志审计都会失控。

你的回答：采取你的建议


### 问题 3：旧 Executor 和旧 ToolManager 是否继续保留兼容？

修正说明：
第一轮问题里把旧 Executor 写成“legacy 回退”，这是一个文档级架构误解。旧顺序 Executor 从未作为正式执行架构完成，也无法解决新 ReActExecutor 解决不了的问题，因此不能把它描述成新链路失败后的可靠 fallback。

建议：
Tools V1 不以兼容旧顺序 Executor 为目标。正式链路应直接收束为：

```text
ReactAgent
  -> Analyzer
  -> Planner
  -> ReActExecutor
  -> 新 ToolRegistry / ToolManager / ToolRuntime
  -> ToolResult
```

旧 Executor 的处理策略：

```text
旧 Executor:
  仅作为早期原型/历史诊断参考或后续清理对象。
  不作为新 ReActExecutor 失败后的自动回退路径。
  不作为 Tools V1 正式验收目标。

旧 ToolManager 旧逻辑:
  不保留为第二套正式执行逻辑。

新 ToolManager:
  可以保留 run_tool 方法名作为当前代码和测试迁移入口。
  但内部必须使用新的 ToolCallRequest / ToolRegistry / 权限 / 日志 / ToolResult 协议。
```

为什么要问：
这决定 Tools V1 是直接服务 ReActExecutor 新架构，还是继续背负旧顺序执行器的历史包袱。当前结论应以后者为错误理解，正式设计按 ReActExecutor 新链路推进。

你的回答：反正目前旧的Executor逻辑已经不使用了（已经完全使用ReActExecutor这个架构了），所以对应的旧 ToolManager可以完全弃掉，完全使用新的，我的倾向是要使用新的就一次性替换成新的，旧的就没必要保留了。反正旧的ToolManager和Executor当时初期也只是简单实现表示有这个东西，是没有结果详细设计的、还是以后续的新设计为准


### 问题 4：Tools 层是否应该统一面向“结构化 ActionPacket”，而不是自然语言工具指令？

建议：
是。Tools 层只接受结构化参数，不接受模型自然语言命令。例如：

```json
{
  "action_type": "tool",
  "tool_name": "read_file",
  "args": {
    "path": "README.md"
  }
}
```

不要让工具自己解析“帮我读一下 README”这种自然语言。自然语言到结构化参数的转换属于模型和 ReActExecutor 的职责。

为什么要问：
这会影响每个工具的参数 schema、错误分类和测试方式。

你的回答：采取你的建议

## 2. ToolResult V1 协议

### 问题 5：是否将 `ToolResult` 外壳统一为所有工具的正式返回协议？

当前状态：
`ToolResult` 已有：

```python
success
data
message
error
code
```

建议：
保留这个外壳，并扩展为 V1 正式结构：

```python
ToolResult(
    success: bool,
    data: Any,
    message: str,
    error: str | None,
    code: str,
    error_type: str | None,
    retryable: bool,
    tool_name: str,
    provider: str | None,
    started_at: str,
    ended_at: str,
    duration_ms: int,
    trace_id: str | None,
    call_id: str,
    raw_output: Any | None,
    metadata: dict,
)
```

外壳统一，`data` 按不同工具定义不同 schema：

```text
web_search.data       = WebSearchData
command_tool.data     = CommandExecutionData

document_parser.data  = DocumentParseData
math_calculator.data  = CalculationData
```

为什么要问：
这决定 Tool 层是否像 Models 层一样正式工程化，而不是简单返回字符串。

你的回答：可以采取你的建议，处理建议里面的字段还需要哪些字段你看着办，还有是不是应该有一个字段表示这个工具调用是哪一类，比如是搜索那就是search，编辑那就是edit，这种表示本次工具调用时调用哪种工具，包括后续返回工具调用错误时也需要点名这个


### 问题 6：工具失败时是否必须返回 `success=False`，不能把错误包装成成功文本？

建议：
必须。比如搜索未配置、文件不存在、命令超时、权限不足，都应该返回：

```python
ToolResult(
    success=False,
    data={...可审计上下文...},
    error="Search is not configured.",
    code="search_not_configured"
)
```

不建议返回：

```python
ToolResult(success=True, data="Search failed: ...")
```

为什么要问：
ReActExecutor 和 Checker 必须能区分真实成功、失败、可重试失败和需要用户确认。

你的回答：采取你的建议，ToolResult还需要加上工具调用类型


### 问题 7：`message` 字段应该给谁看？

建议：
`message` 是短的人类可读摘要，可用于 Observation 摘要或用户可见 event 的基础材料，但不要放完整 stdout、大文件内容、敏感数据。完整结构放 `data`，原始输出必要时放 `raw_output` 或受限日志。

建议规则：

```text
message:
  简短、可读、可展示

data:
  结构化结果，供执行器和测试消费

error/code/error_type:
  结构化失败信息

metadata:
  trace、策略、provider、脱敏状态、截断状态等

raw_output:
  可选，默认不进入用户可见事件，日志也要按策略截断/脱敏
```

为什么要问：
避免把命令输出、文件内容、网页内容全部塞进用户可见事件。

你的回答：可以采取你的建议，message可以作为给用户查看的执行结果（就像codex这样的）

### 问题 8：ToolResult 是否需要 `artifact` 或 `output_files` 字段？

建议：
V1 可先放在 `metadata.artifacts`，格式统一：

```json
{
  "artifacts": [
    {
      "type": "file",
      "path": "workspace-relative/path.txt",
      "mime_type": "text/plain",
      "size_bytes": 1234,
      "created": true
    }
  ]
}
```

后续如果 artifact 变多，再升级成一等字段。

为什么要问：
这会影响文件工具、文档解析和后续 UI 展示。

你的回答：采取你的建议，这个最好完善一下，和上一个问题的回答里面提到的一样，这个可能会涉及到向用户展示的一些执行过程信息和结果


### 问题 9：ToolResult 是否需要记录 `input_summary` 而不是完整输入？

建议：
需要。工具日志里默认记录参数摘要，不记录完整敏感内容。比如：

```text
read_file:
  记录 path / size
  不默认记录完整文件内容

write_file:
  记录 path / content_length / content_hash
  不默认记录完整 content

command_tool:
  记录 command / cwd / timeout / exit_code
  stdout/stderr 截断

web_search:
  记录 query / provider / max_results
  可记录 URL，不记录完整网页正文
```

为什么要问：
这是日志可观测性和隐私边界之间的平衡。

### 问题 18：Tool 层是否要支持 `dry_run`（模拟执行/预览执行）？

通俗解释：
`dry_run` 表示“按照真实执行流程做参数、安全、权限、路径和影响范围检查，但最后不真正执行产生副作用的动作”。它不是绕过工具执行，而是工具在正式执行前提供一个安全预览。

例如：

```text
write_file dry_run:
  检查路径、权限、是否会覆盖、内容大小，只返回预览，不真正写文件。

delete_file dry_run:
  检查目标文件和删除范围，只返回将删除哪些文件，不真正删除。

command_tool dry_run:
  解析命令、检查 cwd、危险命令和超时配置，只返回“允许/拒绝及原因”，不启动进程。

web_search dry_run:
  检查网络策略和 provider 配置，不真正发起联网请求。
```

建议：
支持，但只对有意义的工具启用。比如：

```text
write_file dry_run:
  返回将写入哪个文件、是否覆盖、内容长度，不真的写

delete_file dry_run:
  返回将删除哪些文件，不真的删除

command_tool dry_run:
  只做安全校验，不执行

web_search dry_run:
  检查 provider 配置，不真实联网
```

为什么要问：
确认流程和未来 UI 预览会用到 dry_run。

你的回答：采取你的建议

## 7. 命令行工具边界
还有一点就是：有时候命令执行出错后返回报错信息Observation观察后模型可以根据错误信息对执行步骤做调整，调整使用正确命令后再次执行，这个需要注意，这个涉及执行器执行步骤的调整，所以这个其实和tool层和ReActExecutor 层都有关系，所以在设计的时候记得检验一下这方面的代码是否有实现，是否可以对于实现错误的命令基于报错信息重新调整。
但是如果报错光是修改这条命令没用（比如编辑文件显示这个文件根本不存在那就需要插入一个创建文件的命令在去做编辑，其实这里还有一个问题那就是走到编辑这步其实编辑内容模型已经生成了，调整方案后再次调用模型生成创建文件的命令，然后还需要再次向模型请求获取编辑的内容因为之前的那个内容相当于丢弃了，这样消耗的token就更多了，就拿这个例子其实是整体计划有问题，应该先检查是否有这个文件，如果没有那就先检查在执行编辑命令，所以模型给的计划需要合理，计划需要往耗费最少token完成任务的方向去设计的），这个就需要模型进行判断并决断后续该怎么做，是大调整完成方案还是小调整，反正这个提示词需要很告诉模型这种情况需要处理
以上提出的问题请联系目前执行层、Planner层、tool层的代码仔细看一下，如果目前可以避免发生这种情况那就好，如果依旧有发生的风险请设计一套解决方案。
所以其实虽然本次是在开发tool，但其实agent层与层之间的关系其实很复杂的，所以需要综合起来进行开发设计

你的回答：采取你的建议


### 问题 25：CommandTool 是否继续默认 `shell=False`？

通俗解释：
这里的 `shell=False / shell=True` 不是“有没有权限”的意思，而是 Python/系统执行命令时是否先交给 shell 解释。

```text
shell=False:
  直接执行一个明确的程序和参数，例如：
  ["python", "-m", "pytest", "tests/test_x.py"]
  优点是更容易校验、审计和限制。

shell=True:
  把整段字符串交给 cmd / PowerShell / bash 解释，例如：
  "pytest | tee out.txt"
  shell 会处理管道、重定向、&&、变量展开、命令替换等复杂语法。
  优点是灵活，缺点是风险和审计难度更高。
```

建议：
V1 不应该完全禁止复杂 shell 命令。更合理的方案是把命令工具分成两条执行通道：

```text
普通命令通道 command_tool / argv mode:
  默认 shell=False。
  适合 python -m pytest、git status、npm test 这类可结构化拆分的命令。
  风险较低，仍受 workspace、timeout、日志和错误分类约束。

复杂 shell 通道 shell_command_tool / shell mode:
  使用 shell=True 或等价 shell runner。
  支持管道、重定向、&&、环境变量展开、PowerShell/cmd/bash 特性。
  默认 high risk。
  默认需要用户显式确认。
  必须先 dry_run/预检查，向用户展示将执行的命令、cwd、可能写入/删除/联网的风险。
  必须记录结构化 logs/tools.log。
```

这样可以满足“尽量所有命令都能执行”的目标，同时避免模型在无确认情况下直接执行复杂 shell 字符串。

风险原因：

```text
shell=True 会放大注入风险
管道/重定向/变量展开/命令替换很难审计
Windows cmd / PowerShell / bash 语义差异很大
```

因此建议：

```text
V1 默认普通命令走 shell=False。
V1 同时设计 shell_command_tool 或 command_tool.execution_mode="shell"。
shell 模式不默认暴露为低风险能力，必须经过风险识别、用户确认、timeout、输出截断和日志审计。
用户确认后才开始真实执行。
```

仍然需要注意：
即使用户希望“所有命令都可以执行”，也建议保留少数绝对阻断边界，例如明显工作区外破坏性操作、格式化磁盘、关机重启、泄露密钥、绕过权限策略等。这些不应只靠确认放行，后续可以放进安全与权限层统一决策。

为什么要问：
这决定命令工具安全基线，也决定 Tools V1 是只支持简单命令，还是支持“复杂 shell + 用户确认 + 审计”的完整命令能力。

你的回答：采取你的建议，但是还是需要过滤一些危险的命令，这种危险命令直接就不需要询问用户了，直接拒绝执行，并返回执行结果，说明拒绝执行原因，这种危险命令可以通过规则去过滤，不过一般的删除命令其实不算是高风险的，顶多让用户确认一下就行了，所以命令其实需要做一个风险校验的，命令风险设定几个等级，对于最后一个等级的高风险就直接拒绝，其他的按照等级分为是否询问还是可以直接执行（当然需要用户在第一次使用agent的时候设置一个配置，为true表示低风险的比如编辑文件可以直接执行不需要询问，如果用户不开启默认为false那后续不管执行什么命令都需要用户确认是否执行）


### 问题 26：CommandTool 是否允许管道、重定向、`&&`、`;` 等 shell 元字符？

当前实现：
已禁止部分 shell metacharacters。

建议：
普通 `command_tool / argv mode` 继续禁止 shell 元字符；复杂 shell 命令交给 `shell_command_tool / shell mode` 处理。

也就是说，不是整个 Tool 层禁止管道、重定向、`&&`、`;`，而是：

```text
command_tool:
  默认安全通道，shell=False，不允许 shell 元字符。

shell_command_tool:
  复杂命令通道，允许 shell 元字符，但 high risk、默认需要用户确认、必须日志审计。
```

允许示例：

```text
python -m pytest tests/test_x.py
git status --short
dir
```

普通 command_tool 禁止、但 shell_command_tool 可在确认后执行的示例：

```text
pytest | tee out.txt
cd x && npm test
powershell -Command ...
```

仍建议默认阻断或进入更严格安全策略的示例：

```text
del /f ...
rm -rf ...
format ...
shutdown ...
读取/上传密钥文件
工作区外破坏性操作
```

为什么要问：
这影响命令工具的可用性和安全性。

你的回答：采取你的建议，包含复杂符号的就走shell_command_tool


### 问题 27：哪些命令默认 blocked？

建议：
V1 默认 blocked：

```text
rm / del / erase / rmdir / rd
format
shutdown / reboot
reg
powershell / pwsh / cmd
curl / wget 带执行或下载脚本用途
任何指向 workspace 外路径的破坏性命令
带 --force / /f 的破坏性命令
```

注意：
删除文件应通过专门 `delete_file` 工具，而不是 command_tool。这样权限、确认和审计更稳定。

这看起来像是多做了一个工具，但整体上反而会降低复杂度。原因是删除操作如果放在命令行里，需要解析很多系统差异和危险写法：

```text
Windows:
  del /f a.txt
  rd /s /q dir
  Remove-Item -Recurse -Force ...

Linux/macOS:
  rm file
  rm -rf dir
  find . -delete
```

如果都交给 command_tool，Tool 层必须理解各种 shell、各种参数组合、路径展开、通配符和递归删除语义，安全判断会很难稳定。

如果拆成 `delete_file`，删除语义就变成结构化参数：

```json
{
  "path": "docs/old.md",
  "recursive": false,
  "confirm": true
}
```

这样更容易做到：

```text
确认路径一定在 workspace 内
确认删除的是文件还是目录
确认是否递归
确认是否匹配敏感路径
确认是否需要用户确认
记录删除前文件信息、大小、hash
返回结构化 ToolResult
写入审计日志
```

所以建议不是“为了设计而复杂化”，而是：

```text
常规删除:
  走 delete_file / delete_files，结构化、安全、可审计。

命令行删除:
  command_tool 默认拦截 rm/del/rd。

复杂脚本里确实包含删除:
  后续交给 shell_command_tool + high risk + 用户确认 + 安全策略层判断。
```

V1 建议先做简单边界：

```text
delete_file:
  只删除 workspace 内单个文件或明确文件列表。
  默认需要用户确认。
  不支持递归删除目录。

command_tool:
  默认不执行删除命令。
```

为什么要问：
把文件破坏性操作从命令工具里拆出去，更容易做安全边界。

你的回答：采取你的建议

### 问题 31：`write_file` / 文件修改工具如何区分新建、覆盖、追加和修改？这些操作是否需要用户确认？

通俗解释：
你说的“把原来文件里的 `a` 修改成 `b`”，本质上属于“修改已有文件”。如果工具直接把整份新内容写回原文件，从文件系统角度看就是覆盖写入；如果工具只描述局部 diff/patch，则是补丁修改。

因此 Tools V1 不应该靠自然语言猜测“这是新增、覆盖还是修改”。模型生成的 `ActionPacket.action_args` 里应该明确带写入模式字段，Tool 层再结合真实文件状态做校验。

建议：
正式文件写入/修改工具使用明确字段，例如：

```json
{
  "path": "src/example.py",
  "write_mode": "create",
  "content": "..."
}
```

建议 `write_mode` 支持：

```text
create:
  只允许新建文件。目标已存在则失败 file_exists。

overwrite:
  用 content 替换整个已有文件。目标不存在时是否允许创建，需要配置或额外字段控制。

append:
  在文件末尾追加内容。

patch:
  按 diff/search_replace/insert_before/insert_after/patch_blocks 做局部编辑。
  包括局部替换、局部插入、局部删除，不覆盖整份文件。

create_or_overwrite:
  允许不存在时创建，存在时覆盖。风险更高，不建议模型默认使用。
```

模型 ActionPacket 示例：

```json
{
  "action_type": "call_tool",
  "action_target": "write_file",
  "action_args": {
    "path": "docs/summary.md",
    "write_mode": "overwrite",
    "content": "新的完整内容",
    "reason": "根据用户要求更新摘要文件"
  },
  "requires_confirmation": true,
  "confirmation_type": "file_overwrite"
}
```

如果是局部修改，建议后续使用 `patch_file` 或 `edit_file`，而不是让 `write_file` 模糊处理：

```json
{
  "action_type": "call_tool",
  "action_target": "patch_file",
  "action_args": {
    "path": "src/app.py",
    "patch_mode": "search_replace",
    "replacements": [
      {
        "old": "a",
        "new": "b"
      }
    ],
    "reason": "按用户要求替换变量值"
  },
  "requires_confirmation": true,
  "confirmation_type": "file_modify"
}
```

确认策略建议：

```text
如果用户没有开启总的写入/修改自动授权开关:
  create 新文件:
    可根据策略不确认或低风险确认。
  overwrite 覆盖已有文件:
    必须确认。
  append 追加已有文件:
    建议确认，至少对代码/配置/敏感文件确认。
  patch/edit 修改已有文件:
    必须确认。
  写入敏感文件:
    high 或 blocked，例如 .env、密钥文件、.git 内部文件。

如果用户开启了总的写入/修改自动授权开关:
  workspace 内普通文件的 create/overwrite/append/patch 可以默认执行。
  但敏感文件、工作区外路径、删除、递归操作、危险配置仍然需要确认或阻断。
```

这里的“总的权限开关”可以设计为：

```text
tools.file_write.auto_approve_create
tools.file_write.auto_approve_modify
tools.file_write.auto_approve_overwrite
tools.file_write.auto_approve_append
tools.file_write.require_confirmation_for_sensitive_paths
```

判断来源建议：

```text
1. 模型通过 ActionPacket.action_args.write_mode / patch_mode 明确声明意图。
2. ToolRegistry 用 ToolSpec schema 校验字段是否合法。
3. Tool 层检查真实文件状态：文件是否存在、是否目录、是否敏感路径、是否 workspace 内。
4. ReActExecutor / 安全策略根据 write_mode + 文件状态 + 用户权限开关决定是否需要确认。
5. Tool 层执行前再次校验，不能只相信模型声明。
```

为什么要问：
覆盖文件和修改已有文件都是常见副作用。必须让模型在结构化指挥数据里明确动作模式，再由 Tool 层用真实文件状态校验，避免靠自然语言猜测导致误写、误覆盖或绕过确认。

你的回答：采取你的建议

需要。model_builtin provider 调用模型时，应使用固定提示词模板要求模型输出 JSON：

```json
{
  "query": "...",
  "results": [
    {
      "title": "...",
      "url": "...",
      "snippet": "...",
      "source": "...",
      "published_at": null
    }
  ],
  "provider_summary": "...",
  "warnings": []
}
```

Tool 层拿到模型结果后必须：

```text
1. 解析 JSON
2. 校验 schema
3. 校验 URL 字段是否存在且格式合理
4. 归一化字段
5. 对缺失证据降级 evidence_level
6. 保留 warnings
```

如果模型只返回总结，没有 URL，不能伪装成真实搜索结果。

为什么要问：
模型联网输出本质还是模型生成内容，需要二次校验。

你的回答：需要，采取你的建议，模型返回的肯定必须是结构化agent可以解析并消费的东西，不然自然语言agent也消费不了啊


### 问题 44：web_search 工具是否负责总结搜索结果？

建议：
不负责。`web_search` 只负责找资料和返回证据。总结应由后续模型步骤完成：

```text
web_search
  -> 返回 WebSearchData
ReActExecutor
  -> 生成 Observation
  -> 如果需要总结，再 call_model
```

例外：
如果 model_builtin provider 天然返回 summary，可以放入 `provider_summary`，但这只是 provider 附带信息，不是 SearchTool 的核心职责。

为什么要问：
搜索和总结分离，才能保持工具结果可审计。

你的回答：是的，联网搜索工具只负责将东西搞到手，至于后续怎么消费工具不需要管


### 问题 45：没有 URL 但有模型联网总结时，web_search 算成功还是失败？

建议：
算“降级成功”或“部分成功”，但必须标记证据弱：

```python

    code="ok_with_warnings",

        "results": [],
        "provider_summary": "...",
        "evidence_level": "weak",
```

为什么要问：
这决定 model_builtin 搜索的验收标准。

你的回答：这个标记一下吧，也算是成功吧，这样的就直接消费模型联网搜索的总结就行了呗，反正联网搜索的每一个网站的内容都必须返回这样我的agent就可以间接的获取不同网页的信息了，这个模型可以对每一个网页做概述总结，但是核心的东西不能丢，比如解决方案、代码等等，这样在agent得到这些网页数据后可以再次调用模型进行整理在做后续的规划从而实现参考网页来完成任务，后续的执行步骤也是参考网页给出的解决方案的


### 问题 46：web_search 是否需要缓存？

为什么要问：
联网搜索有成本、延迟和时效性，缓存策略会影响答案新鲜度。

### 问题 47：web_search 是否和网页正文抓取工具分离？

## 15. ReActExecutor 调用 Tool 的方式

### 问题 60：ReActExecutor 是否继续负责 ActionPacket 业务校验，Tools 只做工具级校验？

建议：
是。分工：

```text
ReActExecutor:
  ActionPacket schema 校验
  action_type 是否允许
  当前 step 是否匹配
  confirmation 流程
  Observation 生成
  Checker 状态转移

Tools:
  tool_name 是否存在
  args 是否符合 ToolSpec
  workspace/risk/timeout/tool enabled 校验
  真实执行
  ToolResult 返回
```

为什么要问：
避免把 ReActExecutor 的执行循环逻辑下沉到 Tools。

你的回答：是在，这本来就是不同层的不同职责，采取你的建议


### 问题 61：工具调用失败后，由谁决定 retry / fallback？

建议：
分层处理：

```text
Tool 内部:
  可以对 provider 瞬时错误做小范围 retry，比如 web_search provider timeout。

ToolManager:
  负责执行级 timeout 和统一错误包装。

ReActExecutor:
  根据 ToolResult.retryable / code / checker 决定是否重试整个 action、换工具、询问用户或终止。
```

为什么要问：
有些 retry 应该在工具 provider 内部完成，有些应由执行器根据任务上下文决定。

你的回答：采取你的建议，分层来retry


### 问题 62：Observation 中是否只放 ToolResult 的摘要，不放完整 raw_output？

建议：
不建议简单定成“永远只放摘要”或者“永远放全量”。更合理的是按规划等级和任务需要决定 Observation 粒度。
建议把 Observation 分成三级：
```text
minimal:
  只放状态、code、关键字段、是否成功、少量标识信息
standard:
  关键字段 + 受控 preview + 少量结构化内容
full:
  明确需要全文参与后续推理时才允许，且仍要受长度、敏感信息和上下文预算限制
```
推荐决策原则：
```text
1. 先看当前步骤的规划等级
2. 再看这个步骤后续是否必须依赖全文内容
3. 再看内容是否敏感、是否过长、是否容易结构化
4. 最后决定 minimal / standard / full
```
可以按下面思路落地：
```text
低风险、偏流程型步骤
  -> minimal
  例如：确认状态、文件是否存在、命令是否成功、工具是否可用
普通读写或搜索步骤
  -> standard
  例如：read_file、web_search、document_parser、普通命令输出
需要逐字依赖内容的步骤
  -> full 或 chunk 化
  例如：精确修改、代码定位、对比差异、抽取原文证据
高风险或敏感内容
  -> minimal 或 standard，优先不把全文放进 Observation
```
建议 Planner 或 ReActExecutor 在规划阶段明确标注：
```text
observation_mode = "minimal" | "standard" | "full"
```
这样执行器就不需要猜，能按规划等级和上下文预算决定是否展示全文、预览还是关键字段。
模型摘要不应默认参与 Observation 生成。只有在任务明确需要“总结内容”时，才由 ReActExecutor 单独发起模型步骤，而不是每次工具返回后都再走一次模型摘要。
举例：
```text
用户只是想知道文件改没改成功
  -> minimal
用户要看搜索结果关键证据
  -> standard
用户要根据全文做精确修改
  -> full 或 chunk
用户要总结长文档
  -> 先工具读取，再由模型单独总结，不是 Observation 自动调用模型
```
Observation 的目标不是保存原始输出，而是为下一步推理提供受控视图。
建议它应包含：
```text
tool_name
success
code
message
observation_mode
data_summary
important structured fields
raw_ref 或 artifact_ref（可选）
```
其中 `raw_ref` 或 `artifact_ref` 只保存引用，不默认把完整 raw_output 塞进模型上下文。
```text
tool_name
success
code
message
data_summary
important structured fields
```

不直接放：

```text
完整大文件内容
完整命令 stdout/stderr
完整网页正文
raw provider response
```

如果模型后续确实需要大内容，应由 ReActExecutor 明确选择读取 chunk 或传递受控摘要。

为什么要问：
Observation 会进入模型上下文，必须控制大小和敏感信息。

你的回答：采取你的建议

## 16. 测试与验收步骤

### 问题 63：Tools V1 单元测试优先覆盖哪些？

建议按“先协议、再调度、再各工具族、最后集成”的顺序覆盖：

```text
1. 协议底座
   ToolResult 外壳字段和 to_dict/to_text 兼容
   ToolResult 失败不伪装成成功

   ToolSpec 参数校验
   必填参数缺失识别
   类型校验和 required_any_of 校验
   只暴露 enabled 工具给模型
   工具别名与正式名兼容

3. ToolManager
   执行前调用 registry 校验
   tool 不存在 / 无 run 方法 / 参数非法时返回结构化失败
   捕获异常并返回 internal_error
   trace_id / execution_id / step_id 传播
   logs/tools.log JSONL 写入
   dry_run 不产生副作用

4. 命令工具
   workspace cwd 边界
   shell metacharacters 拦截
   危险命令拦截
   超时控制
   exit_code 传递
   stdout/stderr 截断
   shell=False 和 shell=True 两条路径的安全边界
   high risk 命令需要确认时的返回结构

5. 文件工具
   路径限制在 workspace 内
   大小限制和分段读取策略
   敏感路径拦截
   覆盖确认
   新建 / 覆盖 / 追加 / 局部修改的模式识别
   删除文件与目录删除的边界

6. DocumentParser
   txt/md/json/csv/pdf/docx/xlsx 成功场景
   格式不支持时的失败场景
   大文件超限场景
   解析失败的结构化返回

7. web_search
   未配置时 search_not_configured
   search_api provider 归一化 WebSearchData
   model_builtin provider 结构化 JSON 校验和证据降级
   network_not_allowed 策略
   provider timeout / 失败 / 空结果场景

8. 执行器接入
   ReActExecutor 工具 action 仍通过 ToolRegistry / ToolManager
   ReActExecutor 不直接执行 shell
   Observation 由执行器根据真实 ToolResult 生成
   确认旧顺序 Executor 不作为 Tools V1 正式调用链路

9. 集成与回归
   最低限度的 end-to-end 工具调用链路
   真实联网搜索测试默认跳过
   真实 provider 测试在显式开关下才执行
   失败码、日志、确认和事件流回归
```

为什么要问：
测试范围决定开发步骤是否能小步验收。

### 问题 67：Tools V1 是否暂不做以下能力？
